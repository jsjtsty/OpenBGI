# 子 opcode 栈效果测量（任务书 3 / K）

复现：`analysis\.venv\Scripts\python.exe analysis\scripts\probe_subop_effects.py --tier A1`，将 `A1` 替换为 `A2`、`B` 或 `C`；再运行 `analysis\.venv\Scripts\python.exe analysis\scripts\build_subop_effects.py`。`C` 档重点读取 `pops`、`pushes`，其他字段不作完整性承诺。

## 已验证

- 探测器在原 exe 中直接运行处理器，并钩住 `FUN_0044d2a0`、`FUN_0044d2c0` 统计线程栈实际弹压；取处理前后的线程 IP 差分，记录处理器消费的额外字节。
- 每项使用四组有区分度的合成栈：全零、递增序列、0–3 循环、边界值混合。线程锁及 CRT 随机数入口打桩，避免把宿主 TLS/锁状态当成子 opcode 效果。
- 当前 796 个有处理器的分发表项均有 4 个样本记录，共 3184 次调用：880 次正常返回、693 次脚本错误、1611 次因未初始化宿主对象或状态而异常/未映射。259 个子 opcode 至少有一个正常样本；这些正常样本的线程 IP 消耗均为 0 字节。**这是样本证据，不单独证明所有处理器都没有立即数。**
- `out/subop_effects.tsv` 当前为 797 行（含一个初始空表项），其中 516 项有弹压数：A1 96/96、A2 63/126、B 82/177、C 275/398。143 项在四种样本下有一致的动态记录，67 项沿用已有指定路径验证记录，64 项只有部分正常样本支持；另有 242 项静态推断。与现有手工记录的动态样本比较，`out/subop_effect_conflicts.tsv` 暂无冲突项。

## 静态推断

- A1 中 37 个宿主依赖处理器从源码逐项静态核对了正常路径弹压顺序。弹压发生在错误/条件分支之前，或每条正常分支的压栈次数相同；`81:DA` 的两个结果分支各压一次。void 处理器的 EAX 调度码保持未知，不用猜测值填表。
- A2 另有 28 个处理器没有条件跳转或循环；按反汇编中直接调用线程栈弹/压函数的次数记为静态推断。生成清单为 `out/subop_static_candidates_a2.tsv`。被调用函数的内部路径仍未穷尽，所以没有据此推断调度码。
- 另有 64 项在至少一组样本中正常返回且弹压一致，但没有四组完整正常样本，标记为“观察到的正常路径”，不声称覆盖全部分支。
- `scripts/analyze_subop_stack_paths.py` 对其他仍未知处理器的控制流图枚举所有可达的正常 `ret` 路径；只有每条路径直接调用线程弹/压函数的次数完全相同，才记入 `out/subop_static_stack_paths.tsv`。共有 177 项满足此条件。它不跟踪被调用 helper 内部的线程栈影响、异常展开或挂起恢复，所以仍标静态推断。
- 全部处理器在索引中都没有直接调用 `FUN_0044d180/1a0/1c0/1e0` 等指令流读取器；动态正常样本也未观察到线程 IP 前进。表中静态记录为“0（静态：未见直接读取器调用）”。间接 helper 的极端情况仍需逐个排除。
- 对已正常返回的处理器，样本结果没有观察到额外字节消耗。建议 C++ 注册表只把确认的弹压数写成固定值；遇到空值或“未知”，继续保持硬错误，不要用参数个数猜测。

## 未知与限制

- 280 项仍没有可接受的弹压数字；主要阻碍是需要真实线程、资源管理器、对象池或输入/显示状态的处理器在合成环境中失败，或 CFG 有循环/间接跳转、不同正常分支具有不同栈效果。错误样本观察到的部分弹栈数不能当作正常语义。未确定项为 A2 62、B 95、C 123；A2 另有一个空分发表项，不执行处理器。
- 现有脚本错误路径被单独计数，但尚未区分“预期参数检查”与“合成参数造成的脚本错误”。也未系统覆盖每个 handler 的宿主状态分支和线程恢复后的延迟压栈。
- 没有发现“已有语义表数字与动态弹压冲突”的条目；`out/subop_effect_conflicts.tsv` 记录核对结果。后续发现的冲突要补入该表并调查分支、嵌套处理器或线程初始化原因。

## 对 C++ 实现的直接建议

将 `out/subop_effects.tsv` 中已测的 `pops`/`pushes` 用作注册表候选，并保留置信度列供人工审核；静态候选与动态指定路径分开标注。不要把返回码当成表达式栈结果，也不要把等待对象恢复时延迟压入的值合并进处理器即时 `pushes`。
