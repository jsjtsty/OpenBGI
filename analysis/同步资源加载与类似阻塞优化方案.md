# 同步资源加载与类似阻塞优化方案（2026-11-09）

基于 `8677ced` 的代码检查。本文保留初始设计；第一阶段的图片/音频后台解码现已实现，见[实施与验证](后台资源解码实施与验证.md)。预取及其他路径仍是后续方案。此前人物渐变修复已提交；单次读档回放测得的约 51 ms / 131 ms 图片准备长帧及约 20 ms 音频加载长帧，是优先处理的已知案例。不能把这些调用的总耗时全部归因于磁盘：目前没有逐阶段分解 mmap 缺页、DSC 解压、CBG/音频解码、转换、上传记录和资源分配。

## 1. 结论与顺序

优先级建议为：**分阶段计时 → 图片和音频后台解码 → 有界预取 → 文字与命中掩码优化 → 其他 GPU 特效路径**。

后台解码主要减少主循环停顿；预取才可能消除请求资源时的等待。缓存解决重复请求，不能消除首次加载成本。已有 mmap、ARC 成员哈希索引、128 MiB 图片 LRU、64 MiB PCM LRU，不应先通过更换哈希容器或扩大缓存来代替这两项工作。

## 2. 当前调用路径

| 路径 | 当前行为 | 优先优化 |
| --- | --- | --- |
| `90:10` 图片 | `load_shared → open_media → DSC → CBG/plain → 像素转换 → upload_slot` 全在调用线程；缓存命中仍需上传 | 后台 DSC/图片解码，保留 GPU 所在线程提交；准备命中直接使用共享像素 |
| `A0:11/12/20/21` 音频 | PCM 缓存未命中时同步完整解码；intro/loop 两文件还会拼接 PCM | 先后台完整 PCM 解码，维持现有播放/循环接口；长 BGM 后续再流式化 |
| BM 序列 | 已有 `SequenceService`、Worker、Poll 等待，但加载初始资源仍同步 | 复用操作生命周期模式；检查大文件初次解析、排队和过期结果提交 |
| OP | 已有异步准备、音视频队列和流式 PCM | 保留专用时钟和队列，避免被普通图片预取占满解码资源 |
| 文字渐显 | 每句已经只排版一次，字体/字形也有缓存；但每次 reveal 恢复整块旧文本、CPU paint、上传临时图再合成 | 优化每次 reveal 的像素处理与上传区域，不重复建设已有排版/字形缓存 |
| 菜单命中掩码 | `panel.cpp::show()` 对存在的位图掩码调用 `read_slot()`，等待 GPU 并生成 hit bits | 对静态资源由 CPU 解码像素直接生成命中位；按内容版本缓存 |
| 缩放/扭曲/部分背景特效 | 部分路径 GPU 下载 → CPU 处理 → 上传；已有缓存，但动态参数变化会重新计算 | 根据实际调用频率和像素量迁到 GPU，或消除重复 CPU 处理 |
| 字体首次解析 | 分辨率、文件映射、Font 和 glyph 均有缓存，首次系统字体解析/缺字回退仍可能较重 | 分阶段计时后做受控预热；不能把共享 `FT_Face` 直接交给多个线程 |
| 脚本模块、存档与目录 | 模块解压和部分文件读写仍同步；存档小范围读取、目录负索引已存在 | 保留范围读取；热点模块缓存、缩略图预取，写入需不可变快照及完成反馈 |

## 3. 第一阶段：后台解码，保持脚本依赖关系

### 请求与提交

建议由会话持有一个资源加载服务，第一批接入 `90:10` 和 `A0:11/12/20/21`，不要在各 binding 中分别创建临时线程。

```text
资源请求
  ├─ 已准备好且来源有效：主线程提交，当前指令完成
  └─ 未准备好：建立操作、挂起发起请求的 VM 线程
               ↓
       后台读取映射数据 / DSC 解压 / 图片或音频解码
               ↓
       不可变 CPU 结果进入完成队列
               ↓
       主线程验证操作代次与目标 → GPU 上传或 Mixer 安装
               ↓
       VM Poll 完成，发起线程从下一条指令继续
```

不能在资源未准备好时让发起线程继续执行：下一条可能马上查询图片尺寸、复制图片、设置立绘、播放声道。`90:10` 没有返回值，也可以安装 `Poll` 并使用零个延迟栈结果。后台任务不持有 `Ctx&`、`Thread*`、Display、FontLibrary 或 VM 内存指针。

调度器已有 `WaitObject::poll/cleanup`、`Ctx::suspend()` 和结果数量校验。Sequence 和 Movie 可以提供模式参考，但不是未经审查即可复用的完整通用服务。若 VM 处于独占线程模式，应保留既有独占规则；“挂起一个脚本线程”不能表述为所有其他脚本一定继续执行。事件处理、已有时钟运动、音频和呈现仍需正常运行。

### 必须拆开的读取接口

**`open_media()` 当前不只是打开映射，还同步执行 DSC 解压。** 只将后面的 `cbg_decode()` 或 `decode_bw()` 移到后台，会留下这段阻塞。

建议新增职责明确的原始资源接口，例如 `resolve_raw_owned()`：返回来源身份、是否 loose、原始 `OwnedBytes`、压缩标识和必要元数据，不做 DSC。后台统一完成 DSC 和图片/音频解码，再返回共享只读结果。

最小改动阶段仍由主线程管理 ArcResourceFinder 的惰性索引和缓存，只把已经获得所有权的字节视图交给解码任务；不要并发调用当前未同步保护的 finder。mmap 页面的实际触碰可随后台解码发生，但首次目录查询、归档索引构建和映射创建仍可能阻塞，必须单独计时，不能宣称这一步已经消除全部 IO 等待。

若元数据阶段也占明显长帧，再将解析器改为单一 IO 执行线程所有，或在启动阶段构造并发布只读归档目录。需明确缓存命中时的来源校验：目前新增 loose 覆盖文件会立即生效，不能以长期缓存一次“文件不存在”来换取吞吐。严格来源校验与立即完成的快路径如何结合，需要单独验证，不能默默降低覆盖语义。

### 防止旧任务写回新状态

每个操作包含会话代次、请求 ID、目标图像槽/音频声道及其请求代次。

- 读档、重启、退出使旧会话操作失效；取消只分离该请求的等待，不必取消其他请求共享的解码。
- 目标释放、重建或更新请求使旧提交资格失效；不能只检查“这个编号的槽仍然存在”。
- `slot_generation()` 当前主要表示 GPU 槽分配代次，不能替代所有内容版本或请求顺序。新加载尚未创建槽时也要有独立 ticket；音频声道的 stop/unload/替换等操作同样需要明确顺序。
- 完成结果只在拥有目标状态的线程提交；取消结果不能再次修改 base size、vecmap、缓存引用或播放状态。
- 排队和解码错误必须恢复/终止等待，带资源名和 opcode 上下文；不能让 future 异常变成永久 Poll。

显示槽在什么时刻被替换、暂停声道是否保留暂停、何时开始播放，以及加载失败的结果，都需要按既有行为和原版核对。参考 C 实现的 `WaitBmpLoad` 支持后台加载，并有 skip/同步加载窗口分支；此前该参考实现已有与第三作原始二进制不一致的案例，所以应核对第三作对应 opcode，不能直接照搬其分支和错误码。

### 有界调度与内存

当前 `Worker` 是单工作线程，但 `jobs_` 队列无容量上限，析构会排空队列并 join。它限制并发，不限制排队内存，也不保证读档/退出时能迅速取消。不能直接把全部图片、声音、预取塞进去。

建议从少量解码并发开始（例如 1–2 个，依据实测调整），请求按“正在等待的资源 > 即将播放的声音/当前场景资源 > 预测预取”排序，并同时限制：排队操作数、压缩数据持有量、解码输出与临时内存、等待上传的数据量。大任务正在执行时优先级不能抢占它，需避免长 BGM 解码长期挡住短语音。

相同来源的并发请求合并为一份 CPU 解码结果；GPU 图像槽继续独立，避免脚本修改一个槽污染其他使用者。现有 LRU 上限只约束缓存持有量，使用中的 shared_ptr、解码临时缓冲和完成队列必须另计。调度额度不足时排队或取消低优先级预取，不能回退到主线程同步解码。单个超大合法资源需要专门的调度策略，不能用预算限制随意缩小原支持范围。

## 4. 第二阶段：预取，减少可见等待

第一阶段只让主循环不被解码占住，用户仍可能等资源。真正缩短这一等待，需要在对话等待、场景切换准备等空闲时段提前工作。

先利用脚本明确的资源准备意图和运行日志中的资源序列，做小范围、有预算的预取。若利用历史路径预测，应按游戏/归档身份隔离，承认首遍或分支预测会失败，并限制 CPU、IO 和缓存占用。不能直接把脚本中的所有字符串都当资源，更不能执行未来 VM 指令来“预读”。

预测任务只准备资源，不上传到脚本可见槽、不播放声音、不触发剧情状态；预测失败保持静默，真正需求请求才按现有错误语义处理。路径改变或快进时淘汰无关预取；需求请求可接管正在运行的同一解码任务。

此阶段保留现有图片、PCM LRU 作为起点，先记录命中率、淘汰后的短期再加载和实际驻留内存，再决定是否提高容量。增加内容哈希不能直接省去首次解码；ARC 可优先使用归档身份、成员偏移/长度、资源世代来标识资源，避免首次加载为计算全内容哈希额外扫描文件。

## 5. 上传、声音与其他路径

### GPU 提交

图片解码完成后 GPU 上传仍有代价。保持 GPU 操作在现有渲染所有者线程，合并复制提交、复用 transfer buffer，并正确处理未完成上传的缓冲区轮转。可以给后台预上传设置软预算，但不要让需求资源被无限延后；大图分块上传到暂存槽，全部安排完成后再替换可见槽，避免显示半张图。

`Renderer::create_texture()` 当前会在上传后等待 fence，`Display::upload()` 每次申请 transfer buffer。这些可独立审查：同一 GPU 队列已有依赖顺序时，CPU 等待可能不必要；CPU 下载像素、测试读回和截图等真正需要数据的地方则仍须同步。不能批量删除所有 fence。

### 音频

先把完整 BW/PCM 解码搬到后台，复用目前的 Mixer 行为和 64 MiB 缓存，这一版最容易保持声道状态、长度、循环次数和 intro/loop 语义。音频回调继续只消费准备好的样本，不做 IO、FFmpeg 解码或等待任务。

长 BGM 完整解码可能占较大内存，之后可以复用 OP 的流式组件，但 BW 包装、循环起点、intro/body 拼接、重播、查询时长/位置、欠载时钟都要补齐。当前 `PcmStream` 不是通用可 seek/循环的 BGM 实现，不能直接替换所有 Pcm。短 UI 音效和高频语音仍适合共享解码缓存。

### 文字、命中掩码与特效

- 文字先测 CPU paint、旧页 GPU 回读和上传字节量。已有整句布局，不应再为每次 reveal 重排；可保留 GPU 上的旧页，分离固定字形与正在淡入的字形，缩小更新区域，减少整层重传。重叠字形和阴影需要像素一致性测试。
- 静态命中掩码可在 CPU 图片解码后直接生成 hit bits。动态位图缓存键需同时包含分配代次和内容版本，因为 fill/blit/同尺寸 upload 都会修改像素而不一定换槽。动态 GPU 修改后若确需 CPU 命中信息，仍要有明确刷新路径。
- 连续缩放、扭曲、屏幕 effector 优先考虑 GPU 算法。把 CPU 特效放到后台但仍逐帧同步回读 GPU，通常只是移动等待点，还可能产生过期帧；应先消除往返依赖。
- 模块读取及缩略图可做受控缓存/预取；存档写入只能针对不可变快照做后台序列化和 IO，不能由工作线程遍历正在变化的 VM 内存，完成/失败反馈也须保留。

## 6. 实施与验收边界

1. 加载阶段日志：资源身份、缓存命中、解析/映射、DSC、格式解码、像素转换、上传、排队时间及取消原因；同时记录总驻留/进行中内存。先用现有无头读档路径采样，不用截图作为主要定位手段。
2. 接入 `90:10` 和音频加载的后台操作及主线程提交；先不引入预测，不改变存档格式，不把队列问题藏在更大的缓存中。
3. 受控任务执行器测试：指定时刻完成、失败、取消；验证槽释放重用、声道替换、重复请求合并、读档重启、排队额度与退出。现有 Worker 析构排空策略必须一起处理。
4. 确定性离屏测试继续走同一解码/提交逻辑的同步执行模式，不依赖操作系统线程何时完成，也不能无端让缓存命中多等一帧；异步语义另用可控完成时机测试。真实后台性能另测，不用同步离屏模式声称异步收益。
5. 重放当前首槽读档、推进下一句、连续快进、场景切换、存读档菜单、语音/BGM、OP 播放/跳过和退出。核对结果、图像/PCM、脚本返回及错误行为。
6. 看长帧数量和 tick/present 分布、资源等待时间、输入处理间隔、队列峰值与内存，而不是只看平均 FPS。按实际显示帧预算设目标；脚本 250 Hz 调度与显示刷新率不是同一个指标。

建议第一批改动边界是 **阶段计时 + 原始资源视图拆分 + 有界解码操作 + 图片/PCM 接入**。有了分解数据后再决定 IO 线程化、预取和 BGM 流式化的比例，收益与兼容性更容易验证。
