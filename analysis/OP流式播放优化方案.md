# OP 流式播放优化方案

## 目标与现状

《巧可甜恋3》的 OP 通过 `92:F0` 请求 `data02xxx.arc/ac3_opmv1.mpg`。当前 `ArcResourceFinder::read` 将影片完整复制到内存；`MoviePlayer::start` 同步打开视频、使用 `decode_audio` 解码完整音轨并取得首帧，然后返回。视频帧之后逐帧解码，音轨则整体驻留 PCM。历史交互运行中 `92:F0` 总耗时约 217–1165 ms；该数字不是分项基准。ARC 本身已使用内存映射，优化重点是避免整片复制、整段音轨预解码以及主线程同步等待。

目标是在保持现有脚本语义、画面和声音的前提下减少开始播放前的等待，限制内存占用，并保证跳过、结束和退出时及时释放资源。具体延迟目标须通过同设备、同影片的冷启动和热启动基线确定；不预设未经测量的加速倍数。

## 数据路径

```text
ARC 映射中的成员 / 普通文件
       │ 按需读取、可寻址
       ▼
后台媒体任务：FFmpeg 解复用 → 视频解码 → 有界视频帧队列
                           └→ 音频解码与重采样 → 有界 PCM 环形缓冲
                                                  │
主线程：状态/时钟 → 按 PTS 取帧 → GPU 上传          ▼
                                            现有 Mixer → SDL 音频设备
```

### 资源与 FFmpeg 输入

1. 为 `ArcResourceFinder` 增加拥有明确生命周期的媒体资源句柄。普通文件可使用可寻址文件流；未压缩的 ARC 成员使用持有映射所有权的只读视图，限定读取和 seek 边界。资源解析仍保持 loose 文件优先和现有 archive 搜索顺序。不要把依赖 `ArcResourceFinder` 生命周期的裸 `ByteView` 交给后台线程。
2. `AvInput` 支持该句柄的 `read`、`seek` 和 `AVSEEK_SIZE`，不复制整个影片。映射读取按操作系统分页，不等于完全没有磁盘等待；实际 IO 在后台任务中发生。
3. DSC 等压缩成员先沿用现有解压路径作为兼容回退，必要时再单独设计可寻址缓存。区分“不支持流式”和损坏文件，禁止静默播放错误数据。
4. 原先 32 MiB / 10 s 的 FFmpeg 探测参数需要用两个游戏的实际影片验证后按格式分级调整，保证识别可靠；不能仅靠缩短探测强行降低延迟。

### 解码与缓冲

1. 每个播放器实例使用一个后台任务，拥有自己的 demuxer、音视频解码器和资源句柄。读取包后分别解码两个流；保留 PTS、流起始时间和缺失时间戳的回退规则。视频按需转换为 BGRA，首帧优先。
2. 音频按 Mixer 输出采样率转换为交错 S16，用预分配的单生产者单消费者 PCM 环形缓冲传给 Mixer。首版预缓冲以 100–200 ms 为起点，缓冲上限约 0.5–1 s；依据真实设备和解码速度调优。音频回调只消费已有数据、混音并统计，不执行 IO、FFmpeg、分配、等待或线程 join。现有 Mixer 的短时互斥锁需评估；不把方案描述为整个 Mixer 已经无锁。
3. 视频队列以时间和字节双重限制，初始上限例如 4 帧且不超过 48 MiB；以实际尺寸调整，单帧超过限制时允许一帧的最小容量。队列满时后台任务等待，主线程取最接近当前播放时钟且不晚于该时间的帧，落后时丢弃过期帧。所有 GPU 创建、上传和销毁继续在渲染线程。
4. 单一解复用器不可在音频队列满时无限阻塞，导致视频饥饿：使用有界 packet/帧队列和可中断等待；对音视频交错不佳的 MPEG-PS，检查包缓存和队列上限。在受控上限内优先解出还缺少的首帧或预缓冲，达到上限仍无法前进时明确报错或降级，不能无界累积。
5. 静音影片和音频设备不可用时不等待音频；仍按时间推进视频。视频或音频单流缺失、解码错误及短片 EOF 应有明确的启动和结束路径。

### 状态、脚本与生命周期

- 引入 `Idle → Preparing → Playing → Draining → Finished`，以及 `Failed`、`Cancelled`。`Preparing` 期间既要让主循环持续运行，也要允许用户跳过和关闭窗口。失败和自然结束保留可查询结果，避免悬挂等待。
- `92:F0` 的返回值目前用于返回影片时长，不能简单改成“立即返回 1”。后台读取媒体头和时长后，以现有 `WaitObject` 的延迟结果恢复脚本线程：有时长返回毫秒数，未知时按现有约定返回 1，失败返回 0。等待期间仍调度其他线程和处理输入；确认游戏对结果和准备状态的实际依赖后再固定边界。`90:F2` 在准备和播放期间报告活动，`90:F1` 可取消准备或播放；`91:F8` 维持等待影片结束或用户跳过的语义。
- `Preparing` 完成条件为首个可显示视频帧和足够的初始音频，或已确认没有音频。达到 EOF 的短音轨可不足预缓冲阈值直接启动。音频、视频以同一基准同时开始，避免先启动音频再等首帧。
- 停止、跳过、重启与析构需先使当前代次失效、唤醒生产者、请求取消，再在非音频回调线程回收后台任务和 FFmpeg 对象。后台工作不得持有已销毁的 `Renderer` / `Mixer` 引用；旧任务的完成通知不能污染新影片。检查本地 IO、FFmpeg 探测及队列等待的可取消性，并实测外置盘慢读时的退出时间。
- 确定性离屏模式不依赖后台线程调度或真实音频设备：使用同一解码逻辑的同步推进实现，由虚拟时钟按固定顺序产出所需数据。已有阻塞式 `play_movie` 工具适配器继续可用。

### 音画同步与欠载

- 有音频设备且音轨已开始时，视频以实际消费的音频帧数为主时钟，结合首个音频 PTS；明确 SDL 已排队但尚未播放的延迟及其估算，不能把回调提交时间等同于扬声器播放时间。无音轨、设备不可用和确定性模式使用对应的单调 / 虚拟时钟。
- 启动前以视频和音频各自 PTS 对齐，处理媒体起始时间非零和音轨开头偏移。声音 underrun 时输出静音并计数；播放时钟只按实际媒体样本推进，恢复供给后继续对齐。视频偶尔迟到可丢旧帧，不反复倒退。音轨结束但视频仍有内容时平滑切换到连续单调时钟。
- 不因队列满、跳过、无音频或 FFmpeg EOF 产生死锁；状态变化和设备重建不应导致音频回调访问已释放内存。

## 观测与验收

增加可选诊断指标，分别记录：资源定位、首次读取、媒体探测、首个音频/视频帧、达到预缓冲、首帧实际呈现、开始可听播放、停止完成；同时统计队列峰值、PCM underrun、视频丢帧、总内存峰值和主线程最长阻塞。冷启动与热启动分开，至少重复数次，比较中位数、尾部和最大值；分别记录本地盘和外置盘条件。优化前已有 217–1165 ms 仅为历史总耗时样本，不能当作稳定基线或单独归因。

自动测试使用可分发的小型合成音视频和模拟慢速、截断、失败的可寻址输入，覆盖：

- 资源边界、loose 覆盖、DSC 回退、格式探测和不同 PTS；音视频同时就绪、无音轨/无设备、短片 EOF。
- 有界队列、慢生产者、欠载恢复和 A/V 时钟；首帧、结束和跳过状态，准备中取消、快速重复启动、析构和损坏文件；确保 worker 可退出且不使用失效对象。
- `92:F0` 的延迟返回和时长、`90:F1/F2/F3`、`91:F8` 结果，以及离屏确定性重放；保留现有真实游戏影片测试作为集成验证。
- 用户在《巧可甜恋3》实际验证首播、完整播放的音画同步、跳过、重播与退出；同时回归《巧可甜恋2》的 OP。

## 实施顺序

1. 先加分项观测和真实基线，建立可寻址资源句柄与测试，保留现有播放器作为回退。
2. 增加增量解复用/解码、有限视频队列和流式 PCM 源，先在确定性模式验证数据、时间戳及混音。
3. 接入后台准备、播放状态机和脚本异步等待，验证取消、错误及生命周期，再接入音频时钟。
4. 测试真实影片和慢速输入，比较延迟、内存、音画同步与退出行为后调节缓冲；通过后再移除旧的整段音频路径。
