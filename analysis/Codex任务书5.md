# Codex 任务书 5：用原版 exe 当真值（仍然只研究）

沿用 `Codex任务书.md` 的第 0、1、4 节，以及 `Codex任务书2.md` 第 0 节的动态验证手段（`emu.py` / Unicorn、`winstub.py`、`disasm_fn.py`）。**不要修改 `D:\Projects\C++\OpenBGI\src\`、`tools\`、`tests\`**，游戏目录只读，实验脚本放 `analysis\scripts\`，产出放 `analysis\` 与 `analysis\out\`。

本轮只有两个任务，都是**必须用原版代码执行出结果**的任务。前几轮的主要问题是「静态推断」占了大头，而 C++ 引擎实现时多处靠这些推断，结果发现标签是错的。本轮不接受以静态推断作为最终结论。

## 0. 现状（先读）

C++ 引擎 `obgi_run` 已能在无头模式下跑启动脚本，现在停在第 131 帧附近。它能跑到这里，说明大部分已实现的子 opcode 够用，但下面这些是我们**猜的**，需要真值：

### 0.1 已经发现的错误（都来自 `子opcode语义表.md` 里的标签）

| 子 opcode | 表里的说法 | 实际（C++ 实现时对着真实脚本发现的） |
|---|---|---|
| `80:35` | 查找资源并压结果 | 返回资源**字节数**，脚本拿它分配缓冲区 |
| `80:30` | 载入程序块，压结果 | 压的是**载入的字节数**；压 0 会让脚本算出巨大的负数并陷入死循环 |
| `80:88`～`80:8B` | 全局表查找 | 命名**位表**（定义/置位/区间置位/读位），就是 `BGI.gdb` 里那批表 |
| `90:98` | 设置屏幕兼容位图 | 弹 (数量, 地址)，是一组图像槽 id 的列表（-1 为空），用于文字字符位图 |
| `90:37` 等 | 句柄无效报错 | id `0` 是根（屏幕）对象，总是存在，不能报错 |

这说明语义表里标「静态推断」的条目不能直接信。

### 0.2 我们现在的运行器

- 可执行文件：`D:\Projects\C++\OpenBGI\build\windows\src\Debug\obgi_run.exe`（已构建；不要重新构建，也不要改源码）。
- 用法：`obgi_run.exe "E:\Games\Amairo Chocolate 2" --frames 3000`。设置环境变量 `OBGI_LIVE=1` 会把每个子 opcode 实时打到 stderr，格式 `t<线程> ip=<十六进制> <子opcode> -> <压栈值，十六进制，按压入顺序>`。`OBGI_DBG34=1` 另外打印 80:34、80:30、80:88 的参数。
- `--survey <tsv>` 会把未实现的子 opcode 变成「弹 N 压 M 个 0」的占位，用来看脚本还会走到哪里。占位清单会在末尾列出。
- 它不能代表真值，只能用来**对比**。

## 1. 任务

### 任务 S：从 `ipl._bp` 到标题菜单可交互的真实子 opcode 序列（最高优先级）

这是任务书 3 的任务 N 没有完成的部分。上次的产出 `out\boot_subop_sequence_candidate.tsv` 全部标 `SIMULATED`，里面的返回值是桩给的。

做什么：

1. 在 Unicorn 里**运行原版 VM 的真实主解释器和真实子 opcode 处理器**，从 `autoload.arc/ipl._bp` 开始，一直到标题菜单进入等待输入的状态。只允许替换操作系统层：文件读取（读真实游戏文件，`BGI.gdb` 用游戏目录里的原件）、GDI、DirectX/DirectSound、时间函数、窗口消息、线程原语。**子 opcode 的返回值必须来自原版处理器，不得手写桩。** 如果某个处理器因为依赖 DirectX 之类跑不起来，把它列出来，说明替换了什么、替换成什么，并只对这一个子 opcode 允许用桩。
2. 记录格式：`out\boot_truth.tsv`，列：`序号`、`线程`、`程序（归档/成员）`、`ip`、`子opcode`、`弹出的参数（按弹出顺序）`、`压入的值（按压入顺序）`、`返回码`、`是否桩`。字符串参数要同时给出地址和内容（CP932 解码）。
3. 时间用虚拟时钟：每个调度帧推进 16 ms，与 `obgi_run` 一致，这样两边可以逐行对比。线程切换顺序要和原版一致；如果原版调度依赖真实时间，写明你的处理。
4. 对比：用 `obgi_run`（`OBGI_LIVE=1`）输出做逐行对比，写 `out\boot_diff.md`：
   - 前 200 个**第一次出现的差异**，每个给出：两边的行、差异原因（我们的返回值错、我们缺某个副作用、调度顺序不同、你的桩造成的差异等）。
   - 这些差异里哪几个**最先**导致后续分叉，按重要性排序。
5. 同时回答（写在 `启动路径.md`）：
   - 干净环境（没有 `.sud` 存档，`BGI.gdb` 为游戏自带）下，标题画面之前脚本弹出了哪些消息框，原文是什么。我们这里弹出了一条「未满……岁的人不能玩」的提示，请确认原版是否也会，不会的话是哪个返回值不同。
   - 哪些子 opcode 在这段路径里的返回值依赖运行环境（桌面分辨率、系统时间、磁盘空间、注册表、语言环境），分别取了什么值。

验收：
- `boot_truth.tsv` 中从第一行到标题菜单等待输入，**桩标记的行不超过总行数的 2%**，且都有说明。
- `boot_diff.md` 的差异都有原因，不允许只写「值不同」。
- 如果无法在 Unicorn 里跑到标题菜单，写明停在哪个函数、缺什么，并给出已经得到的最长真实序列（至少越过 `system.arc/ipl._bp` 的初始化），不要用桩凑。

### 任务 T：对「我们猜过的行为」逐项取真值

下面每一项都是 C++ 实现里**没有依据**、靠猜写的。对每一项，在 Unicorn 里调用原版处理器，给出精确行为。每项要给出：参数弹出顺序、每个参数的含义和取值范围检查、压入的值、写入的内存/改变的全局状态、错误条件及错误码。

分组：

**T1：被占位顶替、`--survey` 里命中次数最多的操作**（这些决定下一步能不能往前走）
`80:17`、`81:0F`（命中 124 次，压 1 个值）、`80:1C`、`80:12`、`80:14`、`80:18`、`80:19`、`80:0F`、`91:96`、`91:B8`、`91:BA`、`90:B9`、`90:05`、`90:20`。

**T2：返回值或结构是猜的**
- `80:81`（我们压 0）、`B0:C5`（我们压字体数量）、`B0:C6`（我们写 2）、`80:0D`（固定值）、`81:30`（压 0；注意 `80:30` 的教训）、`81:0E`（显示器尺寸）。
- `90:16`：我们写 (指针=0, 行跨度, 宽, 高, 格式, 每像素字节数) 六个 u32，字段顺序和含义请确认；格式 4～6 是否存在。
- `91:8D`（我们压 1,0,0）、`91:8E`（我们压 0）。
- `80:89`～`80:8B`：位序（我们假设每字节低位在前）、返回码映射。
- 主 opcode `6C`：宽度类、标点类的取值规则（我们只做了 CP932 双字节 = 1，其余 0）；`6E` 的截断规则（我们按 `strncpy` 加 NUL）；`73`、`77`、`7C`、`7D`、`7E`、`78` 的真实返回值（我们全按「失败/否」处理）。
- `90:09` 的范围上限、`90:DD`、`80:98` 的含义。

**T3：显示对象设置**
`90:31`、`90:35`、`90:36`、`90:37`、`90:39`、`90:3A`、`90:3C`、`90:3D`、`90:3F`～`90:46`、`90:48`、`90:49`、`90:53`、`90:55`，以及 `91:31`～`91:4A`、`91:55`、`91:3E`/`91:3F`（从属对象）。我们现在只记录参数。要求给出：每个操作改的是对象的哪个字段（给出偏移和 `CDspObj*` 类名），在合成时怎么用（只要说明到「对最终像素的影响」这一层）。特别是：
- 从属对象的位置到底是 `主位置 + 偏移` 还是别的，什么时候更新；
- 对象 id `0` 的根对象具体是什么，哪些操作会作用在它上面。

**T4：窗口平面 `90:80`～`90:89` 与 `91:88`～`92:8E`**
我们创建了平面并存了参数，没有绘制。要求给出：平面的像素格式和清空值、各设置（边框位图、字体、行间隙、摇摆风格、有效区域）在绘制文字时的作用、`90:85` 七个参数各自的含义（我们只确定了第一个是句柄、第二第三个是位置）、`90:89` 读出来的矩形是否包含右下边（我们按含）。

做法：
- 不要用「加桩直接返回」的方式。每个处理器要在真实的线程对象、真实的内存布局下执行；需要全局对象（显示管理器、字体管理器、图像槽管理器）时，用原版的构造函数初始化，而不是手写结构。
- 每项至少用 3 组不同参数运行，包含一个错误参数，说明处理器是否报错、报什么。
- 做不到的项明确写「无法在 Unicorn 中执行，原因：……」，并给出静态分析结论和不确定的部分。**不要把这一项标成已验证。**

产出：
- `out\t_verify.tsv`：每项一行：`子opcode`、`弹出顺序（每个参数的含义）`、`压入`、`副作用`、`错误条件`、`证据（执行/静态）`、`与 C++ 实现的差异（见下）`。
- 对 `0.1` 表里和你这次新发现的错误，**直接改 `子opcode语义表.md` 的原条目**，在条目里加「已验证（原版执行）」，不要只在文末追加。
- 差异清单 `out\t_diff.md`：把你的结论和 `src\bindings\` 里的实现逐项对比（读源码即可，不要改），列出「C++ 实现是错的」的条目，每条给出应该是什么。源码入口：`src\bindings\system_subops.cpp`、`window_subops.cpp`、`plane_subops.cpp`、`graphics_subops.cpp`、`table_subops.cpp`，主 opcode 在 `src\vm\interp.cpp`。

验收：
- T1 全部项和 T2 全部项必须有「执行」证据；T3、T4 至少各一半项有「执行」证据，其余有明确的无法执行原因。
- `t_diff.md` 里每条差异必须附可复现的命令或脚本名。
