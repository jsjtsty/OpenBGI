# 视频：.mpg 与 .bm（BF_Movie / BurikoMV）（任务 E，Claude 研究）

工具：`scripts/arc_list.py`（列 ARC20 成员）、`scripts/read_vtable.py`。`data02280.arc` 全部 7 个成员：`ac2_ed.mpg`、`ac2_op.mpg`、`ef_shuchu.bm`、`ef_shuchu_bl.bm`、`ef_shuchu_wh.bm`、`ef_shuchu_wh_a.bm`、`shuchu.bm`。

## `.mpg`（片头 ac2_op / 片尾 ac2_ed）

【已验证，直接读文件】标准 **MPEG-1 System 流**（包头 `00 00 01 BA`，MPEG-1 的 `0x2_` 标记），视频序列头 1280×720，帧率码 5（=30 fps），包含流 `0xE0`（视频）、`0xC0`（MPEG 音频，推断为 MP2）、`0xBB/0xBE`。没有自定义封装，不需要特殊处理。
【静态推断】原引擎经 Media Foundation 播放：`DCProcPlayMovieByMF`（等待对象）+ `DCMovieRenderer`（渲染器），用脚本子 opcode `91:F8`（弹标志和两个字符串地址，返回调度码 2，播放结束时等待对象结束）。`91:F8` 在 `_bp` 里没有静态出现位置，实际调用来自 `_PlayMovie`（`framework._bs` 偏移 0x75DC）经 compiled 层再到 `_bp` 的路径，需要追踪。
**91:F8 参数（已核对反编译）**：`FUN_00493e60` 依次弹出 标志、文件名、归档前缀；状态在等待对象释放时压栈：0 = 播完，-3 = 无文件名或文件找不到，-1 = 0x80000001，-4 = 0x80000004。标志传给 `FUN_0049e820`，含义仍未知。
**OpenBGI 实现**：已走 FFmpeg（`src/video/`、`bindings/movie_subops.*`）。注意：自定义内存 IO 没有文件名时，MPEG-PS 里的视频流靠 `mpegvideo` 原始解复用器探测，裁剪构建必须保留它，否则视频流会被误判为 mp3；`AvInput::open` 同时接受文件名作扩展名提示。`ac2_op.mpg` 实测 1280×720、30 fps，MP2 音轨可解。播放时画面跟音频时钟，音频结束或无设备时退回墙钟。

## `.bm` = `BF_Movie`（BurikoMV）

类/对象：`YCBFMovie2`（解码器类，RTTI），`DCProcLoadBurikoMV`（整文件加载）、`DCProcLoadBMVHeader`（仅头）、`DCProcDecodeBMV`（解码等待对象）；`92:F1(mode, 路径…)`：mode=0 装 `DCProcLoadBurikoMV`（0x660 字节对象），mode≠0 装 `DCProcLoadBMVHeader`，返回调度码 2。

### 文件布局

【已验证（对 7 个文件中的 5 个 .bm 全部检查，帧偏移全部落在文件内、单调递增）】

| 偏移 | 内容 |
|---|---|
| 0x00 | 魔数 `BF_Movie_______\0`（16 字节） |
| 0x10 | u32 版本，接受 0x10000 或 0x10001（样本均为 0x10001） |
| 0x14 / 0x18 | 宽、高 |
| 0x1C | 位深：32（带 alpha）或 24 |
| 0x20 | u32，样本 2（RGBA 特效）或 1（shuchu.bm）；疑为帧类型/是否含 alpha 或平面数 |
| 0x24 | u32，样本 15/12/60；疑为帧率 |
| 0x28 | **帧数 N**（4、298…），FUN_004ad640 = `N*4 + 0x80` 即其后头部长度 |
| 0x2C | u32，样本 20 或 0，含义未知 |
| 0x30–0x3F | 保留/未知（样本为 0） |
| 0x40–0xBF | 两张 8×8 字节表（各 64 字节），数值向右下增大（`03 02 02 03 04 08 0A 0C…`、`03 03 04 09 13 13…`）——**疑为亮度/色度量化表**（JPEG 风格），尚未在解码代码中核对 |
| 0xC0 | N 个 u32 **帧起始偏移**（相对文件头；第一个 = 0xC0+4N；`shuchu.bm` 的第一帧在 1384 = 0xC0+4*298） |
| 帧数据 | 每帧压缩数据。`ef_shuchu*.bm` 帧大小约 0.5 MB（4 帧，近似无损/低压缩）；`shuchu.bm` 帧约 60–70 KB，且有每 3 帧一个小包（~2.4 KB）的节奏，疑为关键帧/差分帧交错 |

`ef_shuchu.bm`/`_bl`/`_wh` 的帧偏移几乎相同，说明三者是同一特效的不同着色版本；`_wh_a` 仅 0.5 MB、帧率码 12。

### 解码器（仅静态结构，未完全解出）

- `YCBFMovie2` 构造函数（FUN_004acf80）初始化 256 项的浮点 **YCbCr→RGB 查表**（多个 0x400 字节表）：说明解码输出经 YCbCr 色彩转换。
- 压缩数据用到：**可变长整数**（FUN_004acc80：7 位一组、高位续位）、**256 符号 Huffman**（FUN_004ac520 读 256 个 varint 频次并建树，取最小两项合并）、**零填充 + 字面量段**（FUN_004ac780：`(跳过长度 varint, 字面长度 varint)` 循环，跳过部分填 0x80）、**逐行位掩码的块预测/拷贝**（FUN_004acd70：每像素 1 个位决定“从上一帧参考位置拷贝（带有符号的 dx,dy，−0x80 表示填 0）”还是“与参考相加的差值”，支持 3/4 通道）。
- 另有 8×8 块处理（FUN_004ad6b0 里把宽高对齐到 8 并做 `(w+7)>>3` 块数计算）。该函数把图像拆成 8×8 块并分配 float/short 缓冲，**更像编码路径**（输入 RGB），说明 `YCBFMovie2` 同时包含编码和解码代码；真正的解码入口候选：FUN_004af400（3559 字节）、FUN_004aebc0（1590 字节）、FUN_004ae6e0（1094 字节）、FUN_004b0550（1717 字节）及 0x4b0xxx–0x4b2xxx 的块处理函数（IDCT/量化/反量化/Huffman 位流）。
- 结论：**BF_Movie 是自研 DCT 类编解码（YCbCr、8×8 块、Huffman、差分帧）**，要完整复现必须逐函数逆出，工作量接近 CompressedBG 的数倍。

### 脚本侧接口（静态推断）

`.bm` 的使用方式像“带 alpha 的动画精灵/特效”（`ef_shuchu_*` 在剧情脚本 `ac2_00common` 等中被引用；`ef_love` 也有引用），不是整屏视频：
- `92:F1` 加载/读头；`90:E0/E1/E4/E5/E8` 在管理器（`FUN_0044a5a0` / `FUN_00426b10`）里创建/配置对象（疑为 BMV 播放对象或其显示对象）；
- `90:F5` 释放，`90:F6(3 值，同步或异步)`、`90:F7(值，地址)` 取帧/状态，`92:F2`（解析资源路径并 FUN_004094d0）、`92:F4`（FUN_004096a0）为 BMV 打开/取帧相关；`90:F1/F2/F3` 与 `92:F0` 是另一个视频相关簇（`scrsnd._bp` 偏移 0x1A30 处理器用到，用于音视频同步的“电影类”命令）。
- 需要静态位置：这些 opcode 的静态出现数都很小（≤12），所以实现优先级低于图像/文字/声音。

## 对 OpenBGI 的含义

1. `.mpg` 已实现（FFmpeg）；剧情中很可能只有 OP/ED 用到。
2. `.bm`：先确认游戏流程里哪些特效实际被调用（`ef_shuchu_*`、`ef_love`、`shuchu.bm`）；若只用于少数过场，可先**跳过或用占位**（黑场/淡入淡出），后期再解码器逆向。
3. 如需完整复现 .bm，另立一个“BF_Movie 解码”研究任务：从 FUN_004af400 起逐函数。
