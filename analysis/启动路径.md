# 启动路径与自动读取分支（任务 N，进行中）

复现：`analysis/.venv/Scripts/python.exe analysis/scripts/probe_title_autoload.py`；`analysis/.venv/Scripts/python.exe analysis/scripts/verify_message_effect.py`。前者是带自动桩的研究 VM，后者在 Unicorn 中执行原版对话框处理器并对地址解析、系统对话框打桩。

【已验证】原版 `B0:82` 在两种对话框类型与多个用户选择结果下均弹 3、压 1，正常返回 0。旧自动桩错误地压 2，导致此对话框之后的原型轨迹发生栈偏差。

【静态推断】`title._bp+0x85` 根据全局 `0x774` 判断是否进入自动读取流程；开启时 `+0x95` 对全局有符号 16 位槽号 `0x15e` 与 0 比较，槽号小于 0 即跳到 `+0xc0` 的失败对话框分支，根本不会执行前面的存档加载调用。关闭自动读取时跳过该分支。

【未知】尚无不依赖环境桩的原版启动序列，也未证实全新无 `.sud` 环境中所有全局默认值和其他分支。现有多线程原型包含错误的资源存在性近似和自动桩，不能用作原版启动顺序或参数真值。

【对 C++ 实现的直接建议】按真实 `B0:82` 的弹 3、压 1 实现；将自动读取开关、槽号与存档加载结果区分。不要根据对话框出现就推断一定发生了存档文件读取。

## 可复核的分支证据

【静态推断】`autoload.arc/ipl._bp+0x02..+0x07` 写全局 `0x774=1` 并保留作为参数，随后调用 `system.arc/ipl._bp`；后者在 `+0xbbc..+0xbc2` 将其局部值写回 `0x774` 并调用 `title._bp`。`title._bp+0x85..+0x8a` 读取此标志：零则跳过到 `+0xe4`；非零继续读取 16 位 `0x15e`。`+0x95` 在槽号小于零时跳到 `+0xc0`，装载 `yesnownd._bp` 并传 17；槽号不小于零才先调用 `+0xb3` 指向的已加载程序。`yesnownd` 处理的对话文本为“オートロードに失敗しました”。具体各路径的可达性仍受先前全局变量和分支影响。

【已验证：当前文件与带桩原型】当前 `BGI.gdb` 解出的全局块在 `0x15e` 处为有符号 -1，`0x19f` bit 7 为 0。`probe_title_autoload.py` 记录的原型写入包括 autoload 对 `0x774` 写 1、系统入口再次写 1；这些写入只证明带桩模拟轨迹，非原版整机动态追踪。原版为何采用该存档状态、干净环境是否相同尚未核对。

【已验证（原引擎处理器，依赖打桩）】`B0:82` 的源代码中有两个 `FUN_0044d2c0` 调用，但它们分别位于互斥分支；两种模式、两个标志和三种对话框返回值共 12 个样本均实际压一次。此前 `vm_mt_trace.txt` 的 `AUTO-STUB pops=3 pushes=2` 把两支相加，从这一步起不能信任其后栈状态；应避免用它断言标题能否进入或存档是否正常。

【模拟实验】`vm_mt.py` 已修正该指令的弹 3、压 1，默认遇到对话框时停止；可通过 `--dialog-result 0` 或 `--dialog-result 1` 明确指定模拟结果。以当前 GDB 和仍存在的 AUTO-STUB 执行 300 帧：模拟结果 0 时根线程结束；模拟结果 1 时进入 `title._bp` 的持续循环。轨迹分别为 `out/vm_mt_dialog_0.txt` 和 `out/vm_mt_dialog_1.txt`。这些只说明模拟分支差异，未证明真实标题资源已正确载入或菜单可交互，不能替代原版启动轨迹。

【静态证据与模拟实验】`analysis/.venv/Scripts/python.exe analysis/scripts/probe_archive_group.py` 在研究 VM 中观察到 `system.arc/ipl._bp+0x1087` 将 `sysgrpxxx.arc` 注册为包含 `sysgrp.arc` 的资源组；原版 `80:38 → FUN_004743d0` 也确实构造并注册 `DCArchiveComplex`。本机 `sysgrp.arc` 索引中存在 `SGDialog990017` 和 `SGDialog990017_sc`。旧 `80:34` 桩只看程序语料表，误判前者不存在，从而使用系统消息框 `B0:82`；不能断言这就是原版路径。

`analysis/.venv/Scripts/python.exe analysis/scripts/vm_mt_group_probe.py` 使用资源组和真实 ARC 索引做近似，记录 `out/vm_mt_group_probe.txt`：300 帧内 81 次索引命中、89 次未命中；两个上述对话框资源均被判存在，模拟转入自绘对话框及图像加载，而非旧轨迹的 `B0:82`。资源解析优先级、文件覆盖、图像、输入、线程及其他子指令仍有桩，注册成功也是假设；因此两种模拟结果均不能证明实际菜单状态或真实资源读取顺序。

同一脚本另输出 `out/boot_subop_sequence_candidate.tsv`：每条含模拟帧、线程、程序和偏移、子 opcode、调用前最多 12 个环形栈槽（栈顶在前）、处理后游标、模拟调度码和桩说明。所有行均标为 `SIMULATED`；12 个槽是上下文快照，不代表各指令均弹 12 个参数。该文件用于选择下一批要用原版验证的调用，不满足任务要求的真实启动序列。

【模拟实验与静态文件】`scripts/probe_title_resources.py` 观察到系统入口和标题分别以 `data06xxx.arc/sc._bsi` 调用 `80:35`；当前 AUTO-STUB 一律压 0，因此会跳过后续读取和 `81:D8` 的资源加载路径。本机 `data06000.arc` 确实包含 `sc._bsi`，解压结果为 1110953 字节；但 `data06xxx.arc` 与该归档的实际映射及原版 `80:35` 返回值仍未验证，不能仅凭同名成员就把桩改成真实返回值。

【已验证（原引擎处理器与查找包装；底层读取打桩）】`scripts/verify_resource_size.py` 确认 `80:35` 先弹成员名、再弹归档名，压读取所得长度，正常返回 0。包装优先查找散文件；散文件无结果时才尝试给定归档，归档读取返回高位错误码时转成 0。测试覆盖散文件命中、归档命中及错误，但未实现实际文件读取、资源组匹配和失败回退，不能推断上述 `data06xxx.arc` 的实际值。

## GDB 缓冲和装载包装

【已验证（原引擎处理器；1 MiB 缓冲为合成数据）】`scripts/verify_gdb_buffer.py` 分别在偏移 0 和 `0xffffc` 对 `80:82`、`80:83` 实际执行四字节往返拷贝：前者先弹长度、源地址、GDB 偏移并写 GDB；后者先弹长度、GDB 偏移、目标地址并从 GDB 读。正常路径都弹 3、压 0、返回 0。长度为 0、偏移大于等于 `0x100000` 或长度/终点越界的错误路径已静态确认但尚未动态验证；整数加法回绕也需进一步确认。

【已验证（原引擎包装，加载器打桩）】`80:80` 按顺序压底层加载器输出的两个 u32 和状态；状态 0、`0x80000001`、`0x80000002` 分别映射为 0、1、2，其他值原样压栈；处理器返回 0。当前 GDB 解码内容在 `+0x14/+0x18` 两个字段均为 0，但 `FUN_00479260` 还会调用 `FUN_0047daa0` 校验并可能用当前窗口状态替换，不能据此证明原型硬编码的两个 0 与真实运行一致。

【已验证（原引擎失败路径；文件查询/SDC 失败打桩）】`verify_gdb_buffer.py` 让原版 `FUN_00479260` 的文件查询返回 0，并分别预填模拟调用栈为 `0x55` 和 `0xaa`：`80:80` 分别压入 `[0x55555555,0x55555555,1]` 和 `[0xaaaaaaaa,0xaaaaaaaa,1]`。模拟 SDC 解码长度不符时，分别压入同样的预填值和状态 2。机器码显示这些路径没有写两个输出，因此前两项是未初始化本地栈值，并无可移植的确定数值；其他损坏文件分支仍待验证。C++ 兼容实现可将前两项标为未定义，并决定安全的确定性填充值，而不应当作实际窗口尺寸。

【已验证（原引擎恢复核心和 SDC 解码，部分依赖打桩）】`analysis/.venv/Scripts/python.exe analysis/scripts/verify_gdb_restore.py --native-sdc` 将真实 `BGI.gdb` 交给原版 `80:80 → FUN_00479260 → FUN_004a2360`。经原版解压及恢复核心复制的 1024 字节全局区及 1048576 字节 GDB 缓冲均与 Python 解码结果逐字节一致；窗口校验分别模拟成功和失败时，压栈分别为 `[0,0,0]` 与模拟窗口值 `[640,480,0]`。文件读取、临界区、窗口查询、特殊字符串表和附属结构均打桩，不验证原版文件 IO 或附属列表恢复，不能据此断定实际窗口校验结果。

【静态推断】`80:FD → FUN_004812e0` 压 `DAT_005482c8`，而 `FUN_004377a0` 在解析启动参数时，根据参数文本 `Execute as a launcher.` 设置该标志；已置 1 的状态会保留。引擎创建窗口时也读取这个标志。原型固定压 0 仅对应非 launcher 的一种假设，不能当作所有启动方式的实测值。

【已验证（原引擎处理器；路径数据合成）】`scripts/verify_base_paths.py` 确认 `80:3D` 弹选择器和目标地址；选择器 0 复制引擎主路径并压 1，选择器 1 仅在备用路径非空时复制并压 1，其他情况压 0。原型固定提供游戏目录仅近似选择器 0，真实主、备用路径取决于引擎初始化。

【已验证（原引擎处理器，无宿主桩）】`scripts/verify_resolution_table.py` 对 `81:60` 验证成功、索引超界和两个维度为零的路径。启动模拟现场从栈顶依次传 `960,1280,13` 时，原版压 0 并写入对应尺寸表；旧 `vm_proto.py` 固定压 1 且没有登记，结果错误。研究原型现已按处理器逻辑实现；资源组近似实验重跑后仍得到 4993 条模拟事件和同样的线程终态，但这不证明其他场景不受修正影响。

【已验证（原引擎处理器；部分 shader 创建打桩）】`scripts/verify_shader_thread_ids.py` 显示 `81:6F` 弹 1 压 1，模式 0、2、3 压 1 并更新模式；模式 1、4 在 shader 创建成功时压 1、失败时压 0；其他模式压 0 且不更新。旧原型固定压 0，模式 0 等必然错误；新原型在 1、4 模式默认模拟创建失败，并明确标记该假设。资源组近似实验重跑仍为 4993 条事件；这不是对真实 GPU 结果的验证。

【已验证（原构造函数）及静态推断】同一脚本连续构造三个线程得到 ID 0、1、2；启动函数先构造一个空根节点，才创建 autoload 线程，因此初始 ID 从零开始时 autoload 为 1。模拟器先前忽略根节点并错误地将 autoload 编为 0；现改为 1。上述候选轨迹已重跑，线程 ID 为 1、2、3；若构造器曾在启动前运行过则实际数字可能不同。
