# Amairo Chocolate 2 ML：BGI 脚本 VM 静态分析

主 opcode 补充研究及复现步骤见 `主opcode语义.md`。

分析对象：游戏目录中的 `ac2_ML.exe`，32 位 x86；地址为该映像的虚拟地址（image base 0x400000），对应 `analysis/out/ac2_ML.c`。此报告基于静态反编译与 PE 初始化数据，没有动态执行验证；函数名为 Ghidra 自动命名，指令名称是行为描述，不是原始助记符。反编译器对 fastcall 的 `extraout_ECX/EDX` 和某些返回值恢复不可靠，不能据此断言完整调用约定。

## 执行主循环与调度

`FUN_0049be00`（反编译约第 166020 行）遍历脚本线程，按线程状态判断是否运行、等待或结束。其内部循环调用 `FUN_0044d160` 取一个字节，以该字节索引 `PTR_FUN_0052f660[256]`，检查空项后调用处理器。处理器返回 0 时继续；非 0 时退出本线程的执行片段；每次片段最多执行 0x100000 条，防止单线程无限占用。返回 2 留在当前线程，3 根据 `DAT_0054adb0` 查找线程，4 标记线程终止，6 影响本轮后续线程执行；其他情况推进链表。具体调度状态的完整含义仍待动态确认。无效 opcode 进入 `FUN_00471e50` 报错。

`FUN_00470530`（约第 124079 行）是另一条解释执行路径，使用同一张表，循环直到处理器返回非零或达到 0x10000000 次，并设置错误文本；不应误认为它是唯一主循环。

```text
thread = first_thread
while thread:
    检查状态和等待条件
    repeat at most 0x100000 times:
        opcode = code[ip++]         # 同时保存当前指令地址
        handler = table[opcode]
        if handler == NULL: error
        result = handler(thread)
        if result != 0: break
    按 result 调度或终止线程
```

## 执行上下文和数据

`FUN_0044d160` 将旧 IP 保存于线程对象 +0x7c，+0x80 自增并从 +0x2c 指向的程序内存取字节；`FUN_0044d180/1a0/1c0` 依次读取 1/2/4 字节操作数，x86 小端；`FUN_0044d1e0` 读取带符号的 7 位续接变长整数（SLEB128 风格）。表达式栈是独立的环形 32 位槽数组：+0x18 为数组、+0x10 为槽数、+0x78 为环形游标；`FUN_0044d2a0` 和 `FUN_0044d2c0` 分别弹出和压入一个槽，游标绕回，代码未显示传统溢出检查。另一块调用/局部数据栈以 +0x4c 为底、+0x84 为字节偏移，通过 `FUN_0044d2f0/310` 弹压 4 字节；两者不可混淆。`FUN_0044ce40` 把程序块复制到 +0x2c 的缓冲区并记录名称、长度、偏移，说明线程可持有多个装载的程序块。`FUN_0049d0a0` 将编码地址解析为可访问内存；其标签和边界规则还需逐支验证。错误报告 `FUN_00471ca0` 使用线程、程序名、SP、IP、指令和调用记录。

## 结构

这是 Ethornell / BURIKO General Interpreter：版本字符串、`BURIKO GDB 3.00`、`DSC FORMAT 1.00` 和游戏资源中的 `.arc` 都可在导出或游戏目录看到。脚本 VM 是基于 32 位栈的协作式多线程解释器，低编号提供常量、寻址、访存、算术和控制流，部分高编号处理器体积较大，内部还有子命令，需要独立分析；不能将每个主 opcode 直接等同于一条完整的游戏命令。引擎还包含资源归档、Direct3D 9 纹理/精灵/窗口/特效渲染、文本、输入、音频、影片及持久化等子系统。上述子系统的具体脚本接口尚未全部映射。

## 两级分发与子指令索引

`7F、80、81、90、91、92、A0、B0、C0、D0、E0` 的入口均再读一个字节，在各自 256 项指针表中查找处理器，空项报错。因此完整指令标识通常是 `(主 opcode, 子 opcode)`，并非只有 256 种。已从 PE 的 `.rdata` 导出 11 张表全部非空项，共 796 项，见 `子opcode表.tsv`。这些是静态初始值；表项内容不是语义名称，也未证明所有子指令都会在本游戏使用。`FF` 是另一套特殊扩展机制，不属于这十一张表。

## 启动、帧循环和线程

`FUN_0049b8b0` 初始化各子系统，随后通过 `FUN_0049c120` 读取初始程序并创建线程；调用处提供表达式栈 0x1000 槽、程序区 0x800000 字节、调用/数据栈 0x400000 字节。程序加载函数 `FUN_0044ce40` 从装载块的偏移和长度复制程序数据，并将各块的名称、加载偏移、大小串成链表。主循环每轮调用 `FUN_0049be00` 运行脚本线程，然后调用输入、绘制、音频等更新函数，直到线程列表结束或退出。

`CThread` 构造函数 `FUN_0044c880` 显示每个线程有独立的表达式槽、程序缓冲区和调用/数据栈；+0x0c 连接线程，+0x08 是递增 ID，+0x74 为标志，+0x5c 为等待对象。`FUN_0044d3b0` 设置等待对象并置标志位 1；`FUN_0044d3e0` 调用该对象的虚函数，返回 1 或 -1 时释放对象并清标志。调度器对返回值 0、1、-1 作不同处理，-1 还设置影响本轮的标志；等待对象具体协议仍需逐类确认。

调用指令 `16` 在调用/数据栈保存返回地址，维护单独的调用记录链，之后跳至弹出的目标；`17` 在有返回地址时恢复 IP、移除调用记录，否则返回调度码 4。注意报告中的 opcode 数字以十六进制书写。表达式栈与调用栈相互独立，手写反汇编器必须分别建模。

## 地址编码与调试写监视

`FUN_0049d0a0` 按虚拟地址的高 6 位选择地址空间，低 26 位参与偏移：类别 1 关联线程程序区，类别 2 关联线程数据栈，类别 3 调用线程虚函数解析；其他类别通过全局分段映射表检查并解析。类别 0 及空地址的实际返回值在反编译中受寄存器恢复影响，不应按空函数体推断。分段查找失败调用脚本错误处理。

`74` 调用 `FUN_0049d7c0` 启用或关闭替代写处理器；`75` 注册线程、地址、长度和名称。替代处理器经 `FUN_0049d310` 检查地址区间重叠并弹出诊断，所以这是一套写入监视/调试机制，而非另一套字节码版本。检查时机因指令而异：`60/61/62/6A` 在写前检查，`6F` 在格式化写入之后检查，详见 `主opcode语义.md`。该检查并非所有普通访存都经过。

## 修订说明

初稿误把表达式栈与调用/数据栈合并，现已纠正。上述表针对当前 `ac2_ML.exe` 的初始化映像；任何动态恢复寄存器值、还原全部 795 个子指令的参数和语义、实际脚本覆盖情况，都仍需进一步分析，不能将索引表视作完成的语义表。

## 实际资源样本与装载格式

本次根据 `FUN_00470f00`、`FUN_00471170` 实现了 `scripts/extract_dsc.js`，从 `BURIKO ARC20` 归档提取成员并解码 `DSC FORMAT 1.00`。`system.arc` 的 4 条目录记录每条 0x80 字节；记录前 0x60 字节是名称，其后两个小端 dword 是相对于数据区的偏移和存储长度。数据区从 0x210 开始。实际样本：

- `ipl._bp`：归档内存储 5431 字节，解出 8448 字节；头两个 dword 分别为 0x10 和 0x20f0，正好覆盖 0x2100 字节，`FUN_0044ce40` 将块相对偏移 0x10 后的 0x20f0 字节复制进线程程序区。默认启动来源由 `FUN_00472a20` 指向 `system.arc` / `ipl._bp`，但它可在初始化中配置。
- `framework._bs`：存储 10431 字节，解出 53413 字节，以 `BurikoCompiledScriptVer1.00` 开头。可读取模块名 `framework` 和 94 个符号，例如 `WaitBS`、`_DrawBG`；导出结果为 `out/framework_symbols.tsv`。这些符号的数值暂记为偏移，尚未确认相对于哪个数据基址，也未确认其与 VM 指令的直接对应。

DSC 头 +0x10 是种子、+0x14 是解压大小、+0x18 是 Huffman 符号数，+0x20 起存储 512 个经伪随机序列处理的码长，压缩位流从 +0x220 开始。解码器先建立 Huffman 树，按高位优先读取位流；小于 256 的符号输出字节，其他符号读取 12 位回溯距离并执行 LZ 式复制。全部 800 个 DSC 成员均通过两种实现的交叉检查及边界检查；尚未与原引擎输出做逐字节比对。码长密钥流的低 16 位进位细节曾在初版遗漏，见 DSC格式.md。


启动程序的可复核片段（偏移相对于装载后程序区；这里仅按解码器和处理器读取宽度划分，不表示这些指令一定在运行时按线性顺序执行）：

```text
IP  字节                 操作
00  12 80 23             调整调用/数据栈偏移：SLEB128 +0x1180
03  04 4c 0e             计算基于调用/数据栈偏移的编码地址
06  18 74 07 00 80       根据 32 位立即数编码地址按宽度读取
0b  09 02                按宽度 2（4 字节）写入，并保留值
0d  04 48 0e             计算基于调用/数据栈偏移的编码地址
10  00 00                压入有符号 8 位 0
12  09 02                按宽度 2 写入，并保留值
```

这个片段验证了代码从块偏移 0x10 开始，且核心指令的操作数字节宽度与样本相容；尚未验证栈的初始状态或实际执行路径。

## 线程等待协议：静态追踪实例

【静态推断】`FUN_0044d3b0`（`ac2_ML.c` 92542 行）替换线程 +0x5c 等待对象并设置 +0x74 的 bit 0。下一次 `FUN_0049be00` 调度该线程时通过 `FUN_0044d3e0` 调用对象虚表 +4：返回 0 时跳过该线程；返回 1 时析构对象、清等待位并在当前轮继续执行；返回 -1 时也析构并清等待位，但调度器设置本轮的抑制标志，后续线程不执行脚本。其他非零返回值会继续执行，但 `FUN_0044d3e0` 只对 1 或 -1 清理对象，不能擅自假定其为正常完成。

【静态推断；虚表地址已验证】子 opcode `91:F8` 指向 `FUN_00493e60`（157612 行），它创建 `DCProcPlayMovieByMF`、将其设置为等待对象，子处理器返回 2；`91` 分发包装保留 EAX，已按原始 x86 机器码核对。该类虚表 `0x005156d4` 的 +4 是 `FUN_0045cc20`，+0 是析构入口 `FUN_0045cb60`；更新函数启动影片、在影片状态未结束时返回 0，结束或失败时返回 1。析构路径 `FUN_0045cb90` 将保存的状态压回该线程表达式栈。因结果是在等待对象清理时压栈，不能把创建处理器的返回 2 当作脚本表达式的返回值。具体影片状态值与错误码仍需验证。

- 2026-10-28：原始 x86 机器码复核确认 11 个子分发表包装及正常安全检查路径保留 EAX；详见 `out/dispatch_returns.tsv` 和 `scripts/verify_dispatch_returns.py`。`91:F8` 返回 2 可传至调度器；尚未做动态运行验证。
