## 可复现的实验

【已验证：直接运行原引擎解码器】`scripts/decode_bm.py` 在 Unicorn 内执行 `YCBFMovie2` 构造函数 `0x004acf80` 和原版 `FUN_004aeb40 → FUN_004aebc0`，以单线程的模拟任务池和分配器运行解码，逐帧保存 PNG。帧解码前保留上一帧的像素缓冲区，不能假设任意帧都能从空白图开始解码。示例：

```powershell
analysis/.venv/Scripts/python.exe analysis/scripts/decode_bm.py 'E:\Games\Amairo Chocolate 2\data02280.arc' ef_shuchu_wh_a.bm
analysis/.venv/Scripts/python.exe analysis/scripts/decode_bm.py 'E:\Games\Amairo Chocolate 2\data02291.arc' ef_love.bm 4
py -3 analysis/scripts/survey_bm.py 'E:\Games\Amairo Chocolate 2'
py -3 analysis/scripts/probe_movie.py 'E:\Games\Amairo Chocolate 2\data02280.arc'
```

解码脚本也接受解包后的 `.bm` 路径，第二个参数可限制导出帧数；不指定上限则顺序导出全部。图片写入 `analysis/out/bm_frames/<成员名>/`，仅作临时实验数据。脚本调用原版 EXE，不是独立 Python 实现，也不是两个不同实现之间的差分测试；不能以此声称压缩算法已完全逆出。PNG 输出将原引擎 4 字节像素按 BGRA 转成 RGBA；对于 24 位源，把 PNG alpha 强制设为 255。BGRA 顺序依据位图格式研究，尚未对彩色样本做独立像素级验证。

【已验证：原引擎模拟】`ef_shuchu_wh_a.bm` 的全部 4 帧均已导出，图像显示集中线；`shuchu.bm` 和 `ef_love.bm` 的前 4 帧已导出。前者为 32 位源、后两者为 24 位源。`ef_shuchu_wh_a` 首帧解码得到的 alpha 值均为 204；这只是该帧样本，不能推广到其他文件。输出前 4 帧的 `shuchu.bm` 在将临时分配器改为逐帧复用前后 PNG 哈希一致。

【已验证：静态样本】遍历 7 个 `.bm`，列表及逐项检查结果见 `out/bm_manifest.tsv`。所有样本的帧偏移均非递减、落在对应成员中；上述检查不保证每个压缩帧有效。除非另外注明，下列字段均为小端 u32：

## 帧数据和解码路径

【静态推断】帧入口首先读取 16 个及 176 个变长整数（`FUN_004b0c70`：每字节低 7 位、最高位续接），并调用 `FUN_004b15a0`、`FUN_004b1430` 建立两个符号解码表。之后读取与 8 像素高的块行有关的偏移、每行块掩码及压缩流。`FUN_004af260` 消费工作项：普通工作项经过 `FUN_004b0d60/004b0fb0 → FUN_004af3e0 → FUN_004af400`；32 位 alpha 工作项根据帧数据中的模式调用 `FUN_004b1c80` 或 `FUN_004b1f10/004b18f0`。解码过程还会在目标像素缓冲区上使用历史内容。`0x004acf80` 初始化 YCbCr 转换表，帧中可见 8×8 块变换；这些与图像序列和帧间差分一致，不是仅存储特效参数。

【已验证（原引擎对照，任务池和分配器打桩）】`scripts/probe_bm_frame_dependency.py` 每次重建解码对象，分别将同一帧解码到全 0 和全 255 的目标上，再逐通道比较结果。`ef_shuchu_wh_a.bm` 的第 0 帧输出完全相同；第 1、2、3 帧分别有 535296、531840、535296 个像素的 BGR 三通道保持原始填充值，alpha 通道则在全部像素上依赖输入。24 位 `shuchu.bm` 第 0 帧输出完全相同，第 1 和 3 帧的全部 921600 个像素保持输入 BGR，第 2 帧有 367936 个像素保持输入 BGR。这里比较的是各帧对两种人造初始缓冲的反应，不证明一般帧类型或 alpha 压缩规则。

```powershell
analysis/.venv/Scripts/python.exe analysis/scripts/probe_bm_frame_dependency.py 'E:\Games\Amairo Chocolate 2\data02280.arc' ef_shuchu_wh_a.bm 0 1 2 3
analysis/.venv/Scripts/python.exe analysis/scripts/probe_bm_frame_dependency.py 'E:\Games\Amairo Chocolate 2\data02280.arc' shuchu.bm 0 1 2 3
```

【未知】Huffman 码字规则、8×8 变换的完整数学公式、块掩码和运动/残差的精确编码，以及 alpha 的两种压缩模式尚未完整复刻。当前导出器通过执行原引擎绕过了这些未解部分；不能拿它作为无需原版 EXE 的兼容解码器。

## 独立解码器（已验证，2026-10-28 Claude）

`scripts/bm_dec.py`（纯 Python + numpy，不依赖原版代码）完整实现了 BM 解码；`scripts/verify_bm.py` 在 Unicorn 里用原版解码器逐帧顺序解码同一文件，逐字节比较（32 位源含 alpha 通道）。已逐帧一致：`ef_love` 前 5 帧、`ef_shine` 前 200 帧、`shuchu` 全部 298 帧、`ef_shuchu`/`ef_shuchu_wh_a` 全部 4 帧（`wh_a` 的 alpha 同时覆盖模式 1 和模式 2）。取证脚本 `bm_capture.py` 截获原版每个块行的系数缓冲，与独立熵解码器 90/90 行一致。

【已验证】帧数据布局（偏移相对该帧起始，即 `0xc0 + 4*i` 处的偏移）：

1. 16 个 varint（DC 类别频次）+ 176 个 varint（AC 符号频次），varint 为每字节低 7 位、高位续接、小端排列。
2. `ceil(h/8)+1` 个 u32 偏移：前 `ceil(h/8)` 个是各 8 像素块行的起点；最后一个，24 位源为 `0xFFFFFFFF`，32 位源指向 alpha 数据。
3. 每个块行：`ceil(ceil(w/8)/8)` 字节掩码，**每个块一位，低位在先**（位 i = 第 i 个块，`m[i>>3]>>(i&7)&1`）；随后一个 varint = 系数个数（= 置位块数 × 192）；随后 DC 流，再是 AC 流（DC 流末尾补齐到字节）。

【已验证】熵编码：
- 两棵霍夫曼树由频次表建立（`FUN_004b15a0`）：节点数 2n-1；每轮选出两个最小频次的活动节点，前者为 0 分支，后者为 1 分支，新节点频次为二者之和，直到总和等于总频次。**选择有一个怪癖**：先取第一个活动节点作为候选，再只从下标 `t+1`（t 为第几次选择，0 或 1）起扫描，严格小于才替换，因此第二次选择不会考虑下标 1 的节点（若候选是下标 0）。照搬即可对上，不能换成标准堆。码字按位从高位到低位读取，0 取 child0，1 取 child1。原版的 8 位查表加位走树，与直接走树等价。
- DC：霍夫曼符号 = 类别（0..15），随后读 cat 位，用 JPEG 的符号扩展（`v & (1<<(cat-1))` 为 0 则 `(v | -1<<cat)+1`）；差分累加，对 16 位取模，每个块行开头清零，且**三个平面接续累加**。
- AC：符号 = `大小<<4 | 游程`；0 = EOB；`0x0F` = 跳过 16 个零（不是 JPEG 的 0xF0）；其余 `k += 游程`，读 size 位并符号扩展，放到 `ZZ[k]`，`k += 1`，直到 k ≥ 64。Zigzag 表为标准 JPEG（读自 `0x504da0`）。
- 系数缓冲平面优先：Y 的全部置位块，接着 Cb 的全部，接着 Cr 的全部，每块 64 个 int16、自然序（行主序，行 = 垂直频率）。

【已验证】反变换和色彩（与原版逐位一致）：
- 量化表：头部 `0x40` 起 64 字节为亮度，`0x80` 起 64 字节为色度（行主序，不是 zigzag）。乘以 AAN 缩放表 `s[u]*s[v]`（`s = 1, 1.387039845, 1.306562965, 1.175875602, 1, 0.785694958, 0.541196100, 0.275899379`，原版读自 `0x504e20` 的 float32）。
- 8×8 浮点 AAN 反变换（float32）：先对列（垂直方向）再对行。常数 `1.4142135, 1.8477590, 1.0823922, -2.6131260`。**与 libjpeg 的 jidctflt 有一处不同**：奇部分 `tmp10 = z12*1.0823922 - z5`，`tmp4 = tmp10 + tmp5`，输出下标 3 取 `a3 - tmp4`、下标 4 取 `a3 + tmp4`（libjpeg 里 3、4 的符号相反）。用 libjpeg 版本会在约 3% 的像素上差 ±1 甚至更大。输出不除以 8。
- 取整：浮点结果截断为整数（`cvttps2dq`），算术右移 3 位，加 128，截到 0..255。
- YCbCr→BGR：`R = floor(Y + 1.402(Cr-128) + 0.5)`，`G = floor(Y - 0.34414(Cb-128) - 0.71414(Cr-128) + 0.5)`，`B = floor(Y + 1.772(Cb-128) + 0.5)`（float32，逐项来自 `0x592e70..` 之后的查表），截到 0..255。平面顺序 Y、Cb、Cr，与 JPEG 相同；无色度下采样（三个平面同分辨率）。
- 置位块 **替换** 对应 8×8 像素；未置位块保持上一帧内容（所以随机访问必须从关键帧顺序解起，约每若干帧出现全块行的帧；0 个置位块的帧 = 重复帧）。右、下边缘的块只写可见部分。

【已验证】32 位源的 alpha：位置 = 第二步表的最后一项。版本 `0x10001` 时先读 u32 模式；`0x10000` 视为模式 1 且没有模式字段。
- 模式 1（`FUN_004b1c80`，LZ 式，逐字节写入整幅图的 alpha 通道，起点第 0 个像素，步长 4 字节）：控制字节低位在先，每个控制字节管 8 项。位 = 0：一个字节原样写入当前像素的 alpha；位 = 1：一个 u16 `t`，`dx = t & 0x3f`（≥32 则减 64，范围 -32..31），`dy = (t>>6) & 7`（非 0 则减 8，范围 -7..0），`长度 = (t>>9) + 3`；从 `(x+dx, y+dy)` 起逐像素复制长度个 alpha（允许与自身重叠，即按顺序拷贝）。8 项用完后下一字节是新的控制字节。
- 模式 2（`FUN_004b1f10` + `FUN_004b18f0`）：先是 u32 解码后字节数，接着 256 个 varint 的字节频次表，再是用该表建树的比特流，解出一个字节缓冲。缓冲前 `ceil(blocksW*blocksH/8)` 字节是 8×8 块位图（低位在先，整幅图行主序连续编号）；其后按置位块顺序依次是每块 64（边缘按可见尺寸）个 alpha 字节（块内行主序）。未置位块保持上一帧 alpha。

【已验证】对 24 位源，原版不写 alpha（解码出的 alpha 字节无意义），播放时忽略它。

【未覆盖】`ef_love`（1411 帧）已于后续全部逐字节比对一致（`verify_bm.py`，TOTAL diff 0），`ef_shine` 只比了前 200 帧；其他版本号（0x10000）没有样本；速度：Python 参考实现约 0.2–1 秒每帧（块多时更久），正式实现应当用 C++。

## MPEG 和调用场合

【已验证：文件头及 ffprobe】`probe_movie.py` 从两个 `.mpg` 各取前 16 MiB 送 ffprobe；均识别为 MPEG program stream，视频为 MPEG-1、1280×720、progressive，音频为 MP2。ffprobe 报 `avg_frame_rate=30/1`、`r_frame_rate=60/1`；这两个字段含义不同，不应把 60 直接写成平均播放帧率。本实验只抽取开头，不证明全文件每一包都正常。

【静态推断】`AC2_OP.mpg`、`AC2_ED.mpg` 是开场与结尾影片资源；`DCProcPlayMovieByMF` 是引擎的影片等待对象。故事模块里对两者有字符串引用，但引用不等于该分支必然执行。`.bm` 样本内容包括集中线、光晕等图像序列，与故事脚本引用 `ef_love.bm` 等特效的用途一致；调用链及实参见 `故事脚本用法.md`。两类格式的完整运行时调用场合仍需追踪。
