# 脚本容器、两层 VM 与反汇编验证

研究对象为 Amairo Chocolate 2 ML 的 `ac2_ML.exe`、ARC20 成员和其中的 `_bp`、compiled script、`_bsi`。函数地址为 EXE 的 VA，程序偏移相对于对应 `_bp` 已装载的程序区。证据分为【已验证】、【静态推断】、【未知】；验证是静态文件和实验脚本的交叉检查，并非原引擎执行轨迹。

## 一键复现

在项目根目录，使用 PowerShell 7、Node.js 24.15.0、Python 3.10，游戏目录只读：

```powershell
pwsh -NoProfile -File analysis/scripts/reproduce_task_c.ps1
py -3 analysis/scripts/bgi_dis.py analysis/out/bp_corpus_v2/autoload/00000_ipl._bp --stop-ret
py -3 analysis/scripts/bgi_dis.py analysis/out/main.bs
```

第二个样例需要先运行：

```powershell
node analysis/scripts/extract_dsc.js 'E:\Games\Amairo Chocolate 2\data01100.arc' main analysis/out/main.bs
```

实验输出只位于 `analysis/out/`。`bgi_dis.py` 对 compiled 魔数文件调用 `bs_dis.py`，对 `_bp` 解析原生字节码；原生指令缺省遇到初始空子表项时停止报错。`--allow-null-sub` 可用于结构性查看空项，输出明确标为 `handler=NULL`，不表示原引擎能够执行它。`--start`、`--count`、`--stop-ret` 用于 `_bp`。

## 两层执行结构

【静态推断，样本验证】EXE 中 `FUN_0049be00`（`ac2_ML.c` 166022 行）使用 `PTR_FUN_0052f660` 分发 1 字节原生 opcode；`FUN_0044ce40`（92127 行）将 `_bp` 程序块装载到该 VM。`autoload.arc/ipl._bp` 的原生指令通过 `80:40` 装载 `system.arc/ipl._bp`、调用入口，再通过 `80:41` 卸载。`scrdrv._bp` 将 `script._bp` 装入程序区并保存入口。

【静态推断，样本验证】原生 VM 执行的 `sysprg.arc/scrmain._bp` 程序偏移 0x226–0x2c3 是另一层 compiled script VM 的取指与分发：保存当前脚本 IP，从全局脚本内存基址 `0x6dec8` 加 IP 读取小端 u32，将 IP 加 4，按 `0x64818 + opcode*4` 取出并调用处理器。`scrctrl._bp` 等 14 个 `_bp` 模块初始化该表；静态提取到 456 个不同表项，见 `out/bs_dispatch_candidates.tsv`。`scrctrl._bp` 的 0x3e6 是读取一个 u32 操作数并使脚本 IP 加 4 的帮助函数。主循环与表项初始化均可由 `bgi_dis.py` 复核。

【静态推断】两层 VM 的 opcode 编码和表项不可混用：`_bp` 使用原生字节 opcode 与部分第二字节子 opcode；compiled script 使用 u32 opcode，并由 `_bp` 中的函数处理。`out/bs_opcode_usage.tsv` 记录后者的静态指令位置；`out/subop_usage.tsv` 记录前者的静态子 opcode 位置。两表不是运行时执行次数，也不表示条件分支必然走到。

## `_bp` 程序块

【已验证】扫描当前游戏 29 个 ARC20 归档，发现 110 个 `_bp` 目录项。每个解压块首两个小端 u32 分别指定相对块首的代码偏移及复制长度，范围均位于各自解压数据之内；`FUN_0044ce40` 实际按这两个字段复制。`sysprg.arc` 的两个同名 `playtimer._bp` 内容哈希一致；实验提取使用归档目录序号区分它们。索引为 `out/bp_corpus_v2/index.tsv`。

【已验证，代码/数据边界为静态推断】从每个程序区起点线性扫描到候选最后一个 `17`，将 `17` 后下一个 `12` 视为下一个函数入口，得到 110 个程序、3509 个函数、246356 条原生指令。所有函数都在下一个候选函数起点前以 `17` 结束；其中 12783 个可静态识别的直接分支目标均为同一函数内的指令边界。按独立模式从局部表和全局函数指针初始化提取的 718 个候选目标均位于候选代码范围内；2395 个候选函数入口均与线性边界一致，并以 `17` 结束。明细见 `out/bp_functions.tsv`、`out/bp_function_candidates.tsv`。边界由可复现的指令结构推断，非调试器轨迹；间接跳转和数据区不作可达性保证。

【已验证】在上述 110 个候选代码区内，共有 8968 个原生两级分发指令位置、399 种 `(主 opcode, 子 opcode)`；完整计数和程序列表见 `out/subop_usage.tsv`。其中 7 个 `91:F6` 位置的主、子字节均可识别，但 EXE 初始 `0x00503818` 表的 F6 项为空：在未发现运行时替换的情况下执行将触发原引擎错误。这是**已识别但未实现的表项**，不是本工具凭猜测补出的有效处理器。其条件及复现见 `out/91f6_audit.txt`；运行时是否到达仍未知。扫过候选代码区时没有其他未识别主 opcode 或未列出的子表项。

## compiled script 容器

【已验证，字段用途部分为静态推断】游戏包含 53 个以 `BurikoCompiledScriptVer1.00\0` 开头的成员，剧情成员大多没有 `._bs` 扩展名。小端布局：

| 偏移 | 字段 | 依据及可信度 |
|---|---|---|
| 0x00 | 28 字节魔数 | 53 个样本一致【已验证】 |
| 0x1c | u32，相对本字段位置到后续区段的距离 | 53 个区段起点均 16 字节对齐【已验证】 |
| 0x20 | u32 名称数 | 后接对应数量的 NUL 结尾名称【已验证】 |
| 变长 | u32 符号数 | 每项为 NUL 结尾名称和 u32 值【已验证】 |
| 表末 | 零填充 | 补齐到上述区段起点【已验证】 |
| 区段 | u32 指令与操作数，后接字符串等数据 | 结构性扫描与地址交叉检查【已验证】；运行路径【静态推断】 |

【静态推断，文件结构佐证】`script._bp` 偏移 0x16f–0x2b5 读取第一列表并在条件满足时递归处理名称；0x2bd–0x34d 读取第二列表，将值加上模块载入基址并通过 `80:D2` 注册。该子指令调用 `FUN_004991d0 → FUN_004a6920 → FUN_0045d800`（163049、176072、107314 行），后者按名称建立或更新条目；`80:D4` 经 `FUN_0045d990` 查找。因此第一列表可解释为模块依赖名称，第二列表可解释为段相对符号地址。927 条依赖名称在本数据集中均有同名 compiled 成员（忽略大小写，`framework._bs` 以 `framework` 匹配），含 21 条自引用；加载条件和重名优先级仍需动态核对。完整表为 `out/bs_dependencies.tsv`、`out/bs_symbols.tsv`。

【已验证，边界仍为结构性推断】按处理器的静态读取方式扫描 53 个 compiled 文件，得到 694723 个指令位置、194 种 opcode。每个文件都在候选数据区前停止：末条候选指令为 `001B` 或 `00F4`，后续内容不再匹配表项；所有 121 个导出符号在候选指令起点，其中每个符号到下一符号或候选代码末尾的最后一条指令均为 `001B`。全部 3580 个 `0001` 目标落在指令起点；全部 130963 个 `0003` 模块相对目标落在候选尾部数据区且能找到终止 NUL。明细为 `out/bs_module_audit.tsv`、`out/bs_function_audit.tsv`、`out/bs_boundary_validation.tsv`；`out/main_bs.dis.txt` 是样例。它们强力支持推断的操作数宽度和分段，但不能证明间接调用、分支可达性或所有无名入口的运行时行为。

【静态推断】`0001` 从脚本流取 u32、加当前模块载入基址后压入脚本栈；`0003` 同样形成模块相对地址；`001B` 在调用栈非空时恢复返回位置，`00F4` 返回调度状态 4。其他助记符、参数含义及所有间接函数仍需按后续任务 D 分析。

## `_bsi` 文本表

【已验证】`data06000.arc` 的 `en._bsi`、`sc._bsi`、`tc._bsi` 解压后均按相同结构恰好读完：u32 组数 14；每组是 NUL 结尾组名、u32 条目数，后接重复的 NUL 结尾键和文本。英文样本 `AC2_00common` 有 3698 项，另有 `[name]`、`[selection]` 等；索引见 `out/en_bsi_index.tsv`、`out/sc_bsi_index.tsv`、`out/tc_bsi_index.tsv`。这些是文本资源，不是 `_bp` 字节码。文本编码细节和查找生命周期仍待验证。

复现英文样本：

```powershell
node analysis/scripts/extract_dsc.js 'E:\Games\Amairo Chocolate 2\data06000.arc' en._bsi analysis/out/en._bsi
node analysis/scripts/survey_bsi.js analysis/out/en._bsi analysis/out/en_bsi_index.tsv
```

## 修订记录

- 初稿只识别了原生字节 VM。现根据 `scrmain._bp` 的实际取指和 `scrctrl._bp` 的表初始化，补充 compiled script 的 u32 解释层；不再将两层 opcode 混为一谈。
- 早期只扫描 `_bp` 入口并认为函数边界未知；现以完整候选代码区、直接分支和候选函数表交叉验证 3509 个函数。代码末尾仍注明为静态推断。
- 早期只发现两处 `91:F6`；完整候选代码区扫描发现七处。表项为空的事实与运行时可达性分开记录。
- 剧情 compiled 文件多数无 `._bs` 扩展名；归档中重复名称必须以目录序号保存。

## 已验证

一键脚本处理 110 个 `_bp` 和 53 个 compiled 文件，输出函数边界、静态使用频率及一致性检查；三份 `_bsi` 的组表可完整解析。已列出七处初始空子表项，没有把它们误称为有效处理器。

## 静态推断

两层 VM 的取指、分发、操作数宽度、模块装载和符号注册由 EXE 反编译及 `_bp` 指令交叉推导；代码/数据边界和函数区间通过结构性校验支持，尚未做原引擎单步比对。

## 未知与风险

七处 `91:F6` 是否运行、表是否动态改写；间接调用的实际路径；compiled 非核心处理器是否经间接调用读取额外立即数；无名脚本入口和文本编码细节；静态出现次数与实际运行次数的差异。不能将统计表解释成动态调用频率，也不能保证任意其他版本或损坏文件满足此格式。
