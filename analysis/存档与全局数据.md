`Codex任务书.md` 把 `VM分析.md` 里的 `DCFS FORMAT 1.00` 列为“应为 DSC 的笔误”。**这是我（任务书作者）的错误**：exe 里同时存在字符串 `DSC FORMAT 1.00`（VA 0x5164d0，脚本/资源压缩）和 `DCFS FORMAT 1.00`（VA 0x51510c，存档用的差分快照格式，见下）。Codex 已按任务书把一处改成 DSC；`VM分析.md` 的修订记录 220 行该处需要复核，凡指“存档快照”的应恢复为 DCFS。

## `SDC FORMAT 1.00`（已验证，对 BGI.gdb 与全部 9 个 .sud 的 21+ 块全部解码、校验通过）

引擎函数：编码 FUN_004a23d0（压缩、加密、自检解码）、校验与解密 FUN_004a22b0、LZ 解码 FUN_004a2180、字节加密 FUN_004a2220、压缩器 FUN_004a1d30。

| 偏移 | 内容 |
|---|---|
| 0x00 | `SDC FORMAT 1.00\0`（16 字节） |
| 0x10 | u32 种子（写入时取 `GetSystemTime().wMilliseconds`） |
| 0x14 | u32 载荷长度 C |
| 0x18 | u32 解压后长度 |
| 0x1C | u16 密文字节**和**（模 2^16） |
| 0x1E | u16 密文字节**异或** |
| 0x20 | C 字节载荷 |

- **密钥流**与 DSC 的码长密钥流相同：`product = state*0x015a4e35 (mod 2^32)`，`random=(product>>16)&0x7fff`，`state=product+1`；初始 `state=种子`。加密：`密文 = 明文 + random (mod 256)`；解密：`明文 = 密文 − random`。先对密文做和/异或校验再解密。
- **LZ**（解密后）：控制字节 `c`；`c≥0x80`：回拷，长度 `((c>>3)&0xF)+2`，距离 `(下一字节) + 2 + ((c&7)<<8)`（距离最大 0x801，窗口 2049）；`c<0x80`：后接 `c+1` 个字面字节。
- 复现：`py -3 scripts/sdc_decode.py "E:\Games\Amairo Chocolate 2\BGI.gdb" analysis/out/BGI.gdb.dec`，输出 1226228 字节，以 `BURIKO GDB 3.00` 开头，与头部长度一致，校验通过。

## `.sud` 存档（`UserData\AmairoChocolate2xxx.sud`）

【已验证】整体结构：

1. **头部区 0 – 0xFFFF?**（共 71546 = 0x1177A 字节，所有存档一致）：
   - 0x00：16 字节 `SYSTEMTIME`（年 月 星期 日 时 分 秒 毫秒，小端 u16×8）= 存档时间；
   - 0x10：UTF-8 标题字符串（样本为角色名/章名，补零到 0x90？）；
   - 0xE8–0xF8：几个小整数（样本 `00 02 00 32 c0 00`，含义未知）；
   - `0x140` 附近的字段含义尚未逐项确认，不能直接断定全为脚本名称；
   - `0x848–0x11779`：固定 203×114 的 BGR24 缩略图，逐行紧密排列，无压缩，详见下节。`0x844` 的 4 字节不属于图像。
2. **DCFS 块序列**（从 71546 起，若干个 SDC 包）：每个 SDC 载荷以 `DCFS FORMAT 1.00` 开头。
3. **末尾字符串表块**（一个 SDC 包）：以 NUL 分隔的资源名（`black`、`bg80day`、`ex_bg80day`、`white`、…），推断为存档时已加载/预载的资源列表。

### 存档缩略图（任务 K，已验证）

【已验证：样本与原始脚本交叉检查】`sysprg/userdata._bp` 的 `0x50b–0x519` 将截图按 16.16 固定点比例 `10394/65536`、`10377/65536` 缩放：`1280*10394>>16=203`，`720*10377>>16=114`。`FUN_004031a0` 执行这两个宽高计算；`userdata._bp+0x54f–0x557` 为导出缓冲给出上限 `0x10f32`，`90:15 → FUN_00402c70 → FUN_004092d0` 将图像逐行按像素复制。`203*114*3=69426=0x10f32`。

【已验证：9 个 UserData 样本】图像恰好从存档偏移 `0x848` 开始，长度 `0x10f32`，其后 `0x1177a` 正好是第一个 SDC 头。数据为无行补齐的 BGR24，转换 RGB 后可生成正常的游戏画面缩略图；颜色顺序结合游戏位图格式和图像观察确定，未逐像素与原版截图缓冲区对照。复现：

```powershell
py -3 analysis/scripts/sud_thumb.py "E:\Games\Amairo Chocolate 2\UserData\AmairoChocolate2089.sud"
```

脚本只处理具有本样本布局的存档，发现首个 SDC 位置不匹配时会拒绝猜测；输出在 `analysis/out/`。其他游戏或分辨率对应的存档布局未经验证。

### `DCFS FORMAT 1.00`（已验证，所有块解码后恰好耗尽，帧数/长度一致）

差分快照数组，函数 FUN_00450ab0（编码）/FUN_00450c70（解码）：

| 偏移 | 内容 |
|---|---|
| 0x00 | `DCFS FORMAT 1.00`（16 字节） |
| 0x10 | u32 帧大小 S（样本均为 333114 = 0x5153A） |
| 0x14 | u32 帧数 K（样本 51；最后一块较少，如 3） |
| 0x18 | 第 1 帧原文（S 字节） |
| 其后 | 对第 2…K 帧：与前一帧做差分，序列 `(相同段长 varint) (不同段长 varint + 不同段原文) …` 交替，**从“相同段”开始**，总长累计到 S；varint 为 7 位一组、低位在前、高位续位 |

- 即：一个存档含多个 DCFS 块 × 每块 51 帧，每帧 333114 字节，推断为**脚本 VM 数据内存的快照**（按顺序的回溯点，用于“读档/回滚/回看”）。一个 .sud 样本有 21 个块，约 1000 帧。
- 帧内部布局（333114 字节）与脚本全局变量的对应关系**尚未解析**：需要把 VM 数据区地址（0x80000000+/0x40000000+ 地址空间）与这 333114 字节对齐。下一步建议：把帧 0 与脚本里已知变量（如 `0x400000D6`、`0x80065D50`）对照。

## 对 OpenBGI 的含义

- 读档需要 SDC + DCFS 两个小解码器（均已写出并验证），存档格式可以**直接兼容原版**：先实现“读 .sud → 取最新 DCFS 帧 → 恢复 VM 内存”，前提是 VM 内存布局与原版一致（原版 VM 的地址空间可用我们已知的布局复现）。
- 写档需要 SDC 编码器（压缩算法 FUN_004a1d30 是 LZ77 变体，可自写更简单的版本，只要格式合法）。
- 缩略图为 203×114 的 BGR24 原始行数据；其他版本布局未验证。

## OpenBGI 实现（80:80–85、81:E9）

【已验证】`formats/gdb.*` 的 `gdb_decode`/`gdb_encode` 读写 `BURIKO GDB 3.00` 全部结构：头（总长、窗口 left/top、设置块长 n，样本 0x400）、设置块、u32 m + 全局数据区（m ≤ 0x100000，80:82/83 访问）、u32 数量 + 以 NUL 结尾的键串（80:84 去重追加、80:85 查找）、u32 数量 + 位表（名 NUL、u32 位数、⌈位数/8⌉ 字节）。对清单里全部 GDB 解码结果重编码后与原字节逐字节相同。
【已验证】`80:82/83` 的参数顺序（80:82：大小、地址、偏移；80:83：大小、偏移、地址）、范围检查；`81:E9` 的滚动哈希按 `FUN_00401b70` 实现，测试值由独立的 Python 转写给出。
【设计】原版保存用 SDC 压缩+加密，OpenBGI 没有编码器：80:81 把未压缩的同结构数据写入数据目录的 `BGI.gdb`；80:80 先读数据目录里的，没有再读游戏目录里原版的（SDC 或未压缩均可）。找不到文件时压 `0, 0, 1`（原版此时两个数是未初始化的栈值）。80:81 在原版里不设返回值，这里压 0。窗口位置校验（`FUN_0047daa0`）未实现，原样返回文件里的值。
【注意】`启动路径.md` 里“0x15e 处为 -1”指 0x400 字节的设置块（脚本通过别的子 opcode 访问），不是 1 MiB 全局数据区。
