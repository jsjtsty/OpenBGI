# 主 opcode 语义（任务 L，进行中）

复现：`analysis/.venv/Scripts/python.exe analysis/scripts/verify_main_stack.py`，以及 `analysis/.venv/Scripts/python.exe analysis/scripts/disasm_fn.py 482560 145`。依据 `out/ac2_ML.c` 和原版机器码。

【已验证】在程序边界检查虚函数打桩的原版处理器实验中，`0B` 消耗内嵌字节并复制到目标，`10` 压线程帧指针原值，`11` 将帧指针设置为弹栈值。此前把字段称为 SP 是对反编译字段语义的误判；另一份 C 实现明确将它命名为 FP，并用于数据区局部地址和调用帧。另用原版地址解析器和 CThread 虚表验证标签 0–3 及一组标签 4 页映射，内存池与映射表为合成数据。

【静态推断】`74` 切换 8 个写处理器到含监视检查的实现，`75` 添加监视区间。地址标签 0–3 之外还有可配置的虚拟页映射，标签 3 经线程虚函数解析。

【未知】其余指定主指令、数学指令的完整公式、异常边界、所有地址标签及动态调度返回码尚未全部验证。

【实现对照】C 版 `src/vm/ops_base.c` 将 `10` 实现为 `Thread_GetFP` 后压入表达式栈；`11` 弹值，要求小于当前线程数据区末端，再设置 FP。当前 C++ 版的 `sp` 已承载数据区帧游标，供 `0x04` 局部地址和 `0x16/0x17` 调用帧使用，因此 `10/11` 映射到这个现有游标，不额外引入第二份状态；上界用 `stack.size()` 检查。`10` 压数字偏移、不带地址标签；`11` 是绝对赋值；`0B` 的长度是一个字节，其后的 N 字节是内嵌载荷。标签 3 须调用线程虚函数，不能直接当作普通堆指针。

## 数学样本

【已验证（原引擎对照）】`scripts/probe_main_math.py` 输出 `out/main_math_vectors.tsv`。操作数按先压栈顺序记为 `(a,b,c)`；两条指令都弹 3、压 1，成功时返回 0，均无额外立即数。

| opcode | 公式与指令 | 原版样本 |
|---|---|---|
| `42` | 有符号 32 位 `a,b,c` 扩展后，以 64 位算 `a*b/c`，向零截断，压商的低 32 位；整数实现，不走 SSE 或 x87。 | `(3,7,2)→10`，`(-3,7,2)→-10`，`(2147483647,2,3)→1431655764`。除数 0 的模拟产生 CPU 异常，处理器没有压结果，真实整机异常处理待查。 |
| `43` | 弹 y、x，计算平面角度，单位为 16.16 度；零向量返回 0，其他象限折算到 `[0,360)`。比例、反正切调用及角度换算为 SSE double，末尾转换向零截断。 | `(1,1)→45×65536`、`(-1,1)→135×65536`、`(1,-1)→315×65536`；八个轴向/对角样本见向量文件，边界舍入未穷举。 |

【已验证（样本）；静态推断（一般公式）】`48`、`49` 各弹 1、压 1：输入为 16.16 度，样本分别符合 `sin(angle)` 和 `cos(angle)` 乘 65536 后向零取整。运算通过 SSE double 和对应数学库函数，最终 `cvttsd2si` 截断；0、90、180、270 度样本的输出分别为 `48: 0,65536,0,-65536`、`49: 65536,0,-65536,0`。库函数在所有角度、MXCSR 舍入和极值上的表现还需验证。

【已验证（与原引擎对照，MXCSR=0x1f80）】`46` 弹 4，是两整数端点按 `clamp(numerator/denominator, 0, 1)` 插值并输出 16.16 值，分母 0 时使用比例 0；`47` 弹 3，端点和比例使用 16.16 表示。参数顺序均为先压端点 a、b，之后压比例分子/分母（46）或比例（47）。两者均压 1、成功返回 0。所有转换、除法、乘加均按机器码次序进行 SSE 单精度运算；最后乘 65536，再由 `cvtps2dq` 按 MXCSR 舍入，默认舍入为最近偶数。无效或超出有符号 32 位的转换产生 `0x80000000`（默认异常屏蔽）。

【机器码核对；与原引擎各 3000 组对照】这两条指令随后对转换结果 q 做特殊吸附：`base=q & 0xffff0000`，`fraction=q-base`；fraction 小于 64 时结果为 base，大于 `0xffc0` 时结果为 `base+0x10000`（32 位回绕），否则为 q。临界值 64 与 `0xffc0` 不吸附。复现 `analysis/.venv/Scripts/python.exe analysis/scripts/verify_interpolation.py`，包括分母 0、负值、范围外输入；默认 MXCSR 下 6000/6000 与原版逐位相同。NaN 和未屏蔽异常未覆盖。

【已验证（与原引擎对照）】`scripts/verify_rounding_modes.py` 对 46/47 在四种 MXCSR 舍入模式下分别验证精确的 `+64.5`、`-64.5` 转换：最近偶数为 `(64,-64)`，向下为 `(64,-65)`，向上为 `(65,-64)`，向零为 `(64,-64)`。这只覆盖特定精确中间值，不等于其他舍入模式下全范围的差分验证。

【静态推断；六组原引擎样本】`45` 先弹 z、y、x 角度，再弹源向量地址和目标向量地址；各角度为有符号 16.16 度，源/目标均为三个有符号 32 位分量，不压栈、成功返回 0。按 x、y、z 的顺序旋转，令 `sX=sin(x)`、`cX=cos(x)`，其他轴同理，则：

```text
y1 = cX*y - sX*z           z1 = cX*z + sX*y
x2 = cY*x + sY*z1          z2 = cY*z1 - sY*x
x3 = cZ*x2 - sZ*y1         y3 = cZ*y1 + sZ*x2
目标 = (floor(x3+0.5), floor(y3+0.5), floor(z2+0.5))
```

原版代码以 SSE double 计算三角和旋转，中间按机器码顺序舍入；每个输出的 `floor` 通过库函数和 x87 结果转换，具体受浮点控制状态和越界行为影响。`scripts/probe_rotation45.py` 以默认 MXCSR/FPCW 验证零旋转、三个 90° 轴向旋转、正负输入的 45° 旋转；例如 `(100,0,0)` 绕 z 90° 得 `(0,100,0)`。公式来自机器码追踪而非穷举全部输入，特殊浮点状态与极值未验证。

## 地址解析

【机器码核对】`FUN_0049d1f0` 弹表达式栈后调用 `FUN_0049d0a0`；后者反编译的 `void` 声明丢失了 EAX 返回值。地址 0 返回空指针；非零地址高 6 位为标签，低 26 位为偏移。

| 标签 | 可见处理 |
|---|---|
| 0 | 全局基址 `DAT_005485e0 + offset`；解析器内未显示分配长度检查。`80:70` 分配并清零全局区。 |
| 1 | 程序区基址加偏移。 |
| 2 | 数据栈基址加偏移。 |
| 3 | 调用线程虚表 `+0x14`，传低 26 位偏移。原版 `CThread` 该槽为 `FUN_0044ce20 → FUN_004363f0`，结果是线程私有池 `thread+0x50` 对象内 `+4` 的基址加偏移；虚表子类可覆写。 |
| 4–63 | 查 `0x504c20..0x504d40` 中的标签范围及页表，计算页和页内偏移；没有有效映射时报脚本错误。实际配置、页大小及全部边界尚未穷举。 |

【静态推断】`80:70` 对参数 v≤12 分配并清零 `0x1000 << v` 字节，用作上述全局基址；其他调用者或读写指令可能另行检查边界。

【已验证（原引擎处理器，分配与释放打桩）】`scripts/verify_global_alloc.py` 覆盖指数 0、1、5，检查分配大小、全局基址、原版清零、旧缓冲释放，以及弹 1 压 1、返回 0；超界错误和真实分配器未验证。

【已验证（与原引擎对照；合成映射表）】`analysis/.venv/Scripts/python.exe analysis/scripts/verify_address_resolver.py` 使用原版 CThread 虚表，验证空地址、全局/程序/数据栈/线程池地址及标签 4 的一页映射结果。该测试不验证缺页错误、所有映射配置、越界和子类虚表。

## 写监视

【静态推断】主 opcode `74` 弹值传 `FUN_0049d7c0`；零恢复初始表，非零替换 `09、0A、0C、60、61、62、6A、6F`。`75` 弹名称地址、长度及起始地址，`FUN_0049d2a0` 将当前线程 ID、地址范围和名称挂入全局链表，压注册是否成功。替代写处理器的 `FUN_0049d310` 检查写区间和链表区间是否重叠；标签 1–3 时还要求线程 ID 匹配，命中后显示诊断。各替代处理器的检查发生在写前还是写后需逐个核对。

【机器码核对】`60/61/62/6A` 的替代实现先通过 `FUN_0049d630` 做监视检查，再复制、填充或写字符串；`6F` 的替代实现先调用 `FUN_004a5620` 格式化并写出字符串，之后计算长度并调用 `FUN_0049d310`。因此 `6F` 的诊断发生在写后，不能将所有替代指令都描述为“写入前检查”。`09/0A/0C` 通过 `FUN_0049d410` 检查目标地址，逐元素写入时机仍需动态对照。

【已验证（原引擎替代处理器，监视回调和格式化器打桩）】`scripts/verify_write_watch.py` 以 `old` 作为目标、`new` 作为写入内容，原版 `6A` 调用监视时目标仍为 `old`；原版 `6F` 调用监视时目标已为 `new`。该测试验证调用先后，不验证真实格式化内容或诊断对话框。

【已验证（原引擎对照）】同一脚本调用原版 `74`，分别输入 1、0，验证上述八个主分发表项确实切换到替代地址并恢复初始地址。反编译源中 `FUN_0049d7c0` 唯一直接调用点是主 opcode `74` 的处理器；间接调用或其他运行时写表行为未排除。

【已验证（原引擎对照，分配器打桩）】同一脚本还验证 `75` 的长度 0 与 16 两条路径：前者压 0 且不创建记录，后者压 1，并登记线程 ID、编码地址、长度和名称。记录生命周期、重叠检测的边界及实际对话框未在此测试中验证。

## 补充：`09` 与 `0A` 的弹栈顺序相反（OpenBGI 运行真实 ipl 时发现）

【已验证（反编译 + 真实脚本）】`FUN_00482330`（`09`，写并保留值）先弹值、再弹地址；`FUN_00482390`（`0A`，写）先弹**地址**、再弹值。真实脚本里 `0A` 的写法是 `[值] [地址] 0A`（`*p = 表达式`），例如 system/ipl 的 `load_stack r; ...; op_40; load_stack p; store`。`vm_proto.py` 把两者当成同一顺序，是错的；按错顺序，启动脚本在 `sysprg/fontinfo` 里会向 `0xFFFFFFFF` 写入。`0C`（`FUN_00482410`）的顺序还没单独核对。

## 补充：表达式栈是环形的（OpenBGI 运行真实 scripts 时确认）

【已验证】`FUN_0044d2c0`（压）与 `FUN_0044d2a0`（弹）对表达式栈槽数取模：压满回绕到 0，空栈弹出回绕到末尾，都不报错。编译出的脚本大量用 `09`（写并保留值）作语句而不弹掉结果，循环里每轮泄漏一个槽，原版靠环形栈吸收。OpenBGI 的 `Ctx::push/pop` 已改成环形，子 opcode 的栈效果校验改为按槽数取模。
