# OpenBGI 系统性评审与重设计建议

评审日期：2026-11-03。范围是当前工作区，包括已有未提交修改；不是仅评审 HEAD。本次未修改运行时代码。

## 判断

项目已经积累了有价值的格式解码、VM 指令、混合公式和原版行为研究，但整体仍处在“用 opcode 处理器逐步拼出可运行原型”的阶段。继续单纯增加 opcode 和画面修补，会让兼容问题越来越难定位。

建议保留经过验证的算法，逐步重建运行时骨架：**行为规范 → VM/调度与等待协议 → 显式可恢复状态 → 领域服务 → 平台后端**。优先完成一个目标游戏的可靠运行闭环，再扩大引擎版本和平台范围。

最值得先解决的是运行模型和状态所有权。目录改名、增加接口数量或一次性重写全部渲染，都不能单独解决这些问题。

## 系统性问题

### 1. P1：调度协议发生偏离，已经影响现有测试

证据：`src/vm/scheduler.cpp:108`、`src/vm/core_subops.cpp:144`、`analysis/线程调度.md`、上述失败用例。

当前 `StayThread` / RC 2 直接执行 `++i`。研究文档记录的行为是重新进入当前线程状态检查；是否继续执行，取决于等待对象，而不是 RC 2 本身。已经到期的 `80:5A` 会返回 2 且不安装等待对象，当前实现却额外推迟到下一帧。

同一模块还有两处需要纳入契约核对：

- 切换到不存在的线程时，当前实现返回致命错误；本地原版合成实验记录的是结束本轮调度。
- `WaitObject` 的完成结果只有 bool，无法直接表达研究文档中的 0、1、-1 以及其他非零值的不同清理和抑制行为。

**改法：**逐条实现已验证的调度状态转换，单独建模“处理器返回码”和“等待对象更新结果”。增加 RC 2 无等待、未到期等待、当轮到期、切换缺失目标、抑制后仍更新等待对象等合成测试。不要用“避免死循环”替代兼容语义；诊断预算耗尽时应保留执行位置并报告原因。

### 2. P1：即时返回与延迟完成共用一个栈效果签名

证据：`src/vm/interp.cpp:136`、`src/bindings/sequence_subops.cpp:140`、`:171`、`src/bindings/message_subops.cpp:419`。

`90:F6` 登记为弹 3、压 1。走 `80:53` 开启的异步路径时，它只弹 3，结果在后续 poll 中压入；但解释器在处理器返回后立刻按净变化 -2 检查。默认表达式栈容量下实际是 -3，合法的异步分支会被判为栈效果错误。此处是代码路径可直接推出的缺陷，本次未用真实 BM 文件执行复现。

消息输出使用另一种约定：登记即时压 0，完成回调再手工写 `Thread::expr`。这绕过了统一的参数、返回值验证和 trace。不同 opcode 因而各自发明延迟返回协议。

`80:5C` 的核心实现还提前压 0、忽略输入参数；本地研究记录的则是完成时根据超时或输入压入结果。实现和研究结论应重新对齐。

**改法：**签名拆为 `immediate_pops / immediate_pushes / completion_pushes`，或者等价的分阶段契约。VM 统一接收完成记录、验证并写回，服务和任务不能直接修改线程表达式栈。trace 分别记录发起与完成。

### 3. P1：没有统一的运行时和时间模型，完整声音链路也没有接通

证据：`tools/run/main.cpp:146`、`:152`、`:354`；`src/audio/mixer.cpp:146`；`src/bindings/system_subops.cpp:843`；`src/bindings/message_subops.cpp:86`、`:397`。

运行器在有窗口和无窗口模式下都用 `f * 16` 作为 VM 时间。`90:02` 改变 `frame_ms` 后主要影响呈现节奏；打字、自动等待等又在局部使用固定的 16 ms。窗口运行的虚拟时间也未按真实经过时间推进。

运行器创建了 `Mixer`，却没有打开 `AudioDevice`，也没有离线调用 `mix()`。因此这个入口中声音不会输出，播放位置和淡出等依赖采样推进的状态不会正常前进；脚本读取的播放状态也会受影响。音频单元测试通过并不能证明运行器接线正确。

**改法：**引入 `EngineSession`，统一装配时钟、输入、任务、VM、服务和后端。交互模式按单调真实时间驱动；回放模式按记录的逻辑时间驱动；无声测试也必须有离线音频推进器。

必须区分毫秒时钟、调度轮次、呈现频率和音频采样时间。本地研究尚未证明 `90:02` 会替换等待对象的毫秒时钟，不能简单把 `f * 16` 改成 `f * frame_ms` 就宣称兼容。

### 4. P1：状态分散在闭包里，保存、重启与取消没有共同基础

证据：`src/vm/vm.hpp:76`；`src/bindings/graphics_subops.cpp:63`；`src/bindings/message_subops.cpp:136`；`src/bindings/sequence_subops.cpp` 的私有 `SequenceTable`；`src/bindings/particle_subops.cpp` 的 `World` / `RainWorld`。

等待状态是 `std::function<bool()>`；文字游标、渐显进度、序列解码器、粒子世界、部分尺寸信息隐藏在注册函数创建的 shared_ptr 和 lambda 捕获中。即使复制 `SystemState` 和 VM，也不能恢复一局游戏。

目前有 GDB 全局数据读写，但这不等于具备整局状态保存。已有设计文档要求“所有服务从第一天可序列化”，实现没有对应的状态边界。

**改法：**每个领域有显式 State；等待采用带类型的数据结构，例如 `TimeWait`、`MessageWait`、`DecodeWait`，存储截止时间、对象 ID、操作 ID 和结果目标。回调、future、GPU 对象属于运行设施，不进入持久状态。恢复时按逻辑状态重建它们。

不要求每一轮完整复制所有状态；先实现稳定检查点和逻辑状态摘要，再做文件格式。

### 5. P1：对象生命周期缺少身份验证和统一清理

证据：`src/vm/scheduler.cpp:105`；`src/vm/vm.hpp:82`、`:210`；`src/bindings/sequence_subops.cpp:79`；`src/bindings/plane_subops.cpp:45`。

脚本线程退出只标记 dead，线程列表中仍保留其程序、默认 4 MiB 数据栈和等待闭包。长时间创建并结束线程会持续保留这些数据；原始线程指针捕获也让后续回收变得困难。

异步序列解码完成时只验证目标图槽的尺寸和格式。如果另一个脚本线程释放并用相同尺寸重建该图槽，旧任务仍可能把结果写进新对象。尺寸相等不能证明对象还是原来的那个。

**改法：**内部句柄包含 index 和 generation，任务完成时校验操作代号、所有者和目标代数。线程退出、资源释放、重启和读档都进入统一取消/清理流程，线程实体在安全点回收。

脚本可见 ID 必须保持原版规定的数值和复用语义，通过兼容映射转换到内部句柄。不要把带 generation 的内部整数直接交给脚本来破坏 ABI。

### 6. P1：注册数量掩盖了“已接收但未生效”的功能

证据：`src/vm/vm.hpp:148`；`src/bindings/system_subops.cpp:818`、`:883`、`:921`、`:933`、`:936`；`tools/run/main.cpp:199`。

未知 opcode 默认报错是好的；但已注册处理器里仍有无实际效果的成功路径。例如 `B0:C3` 仅检查归档字体存在便返回成功，并未注册字体；`80:37` 保存的 `search_paths` 在 src 中没有消费者；部分位图效果只消费参数；影片状态查询固定返回 0。

`SubopRegistry::add` 还会静默覆盖同 ID 处理器。系统绑定和后续领域绑定存在覆盖式装配，使最终行为取决于调用顺序，而注册表只暴露最终条目。

显式 `--survey` 作为研究工具合理，但其运行结果不能作为兼容成功证据。

**改法：**建立唯一 opcode 描述表，记录即时/完成签名、实现等级、证据来源、适用版本和唯一实现 owner。重复注册默认失败，必要的替换必须显式声明。严格模式遇到未支持行为应给出明确诊断；原版规定的正常失败返回值则照常保留。研究模式的桩命中应写入结果元数据。

### 7. P2：bindings 已承担领域服务职责，SystemState 变成共享状态集合

证据：`src/bindings/system_subops.hpp`、`graphics_subops.cpp`、`plane_subops.cpp`、`message_subops.cpp`、`panel.cpp`。

绑定层直接处理文字布局、图层合成、输入消费、面板状态机、资源读取和任务创建；`SystemState` 同时包含输入、GDB、路径、运动、窗口、面板、滑块、排版和平台回调。修改一个子系统时，难以判断会影响哪些 opcode 和共享字段。

这与原设计“bindings 仅参数转换、调用服务、结果写回”的原则明显不同。按 opcode 前缀分文件可以辅助逆向查找，但不能作为全部领域边界。

**改法：**按实际状态归属抽出 Input、Scene/Bitmap、Message、Audio、Movie、Resource、Persistence 服务。先移动状态和完整业务操作，再缩薄绑定；不要仅将原大文件内容包进一个 Services 类。

### 8. P2：渲染后端承载了可观察状态和 CPU 图像处理

证据：`src/render/display.cpp:232`、`:409`、`:440`、`:640`；`src/bindings/plane_subops.cpp:94`。

Display 同时维护脚本对象、主从关系、背景特效、地图、CPU 缓存和 GPU 存储。`compose()` 会解析主从位置并修改对象，说明绘制不仅消费状态，也推进部分状态；不同的绘制调用路径可能影响查询时看到的数据，应建立呈现次数无关性测试。

CPU 特效和命中掩码会走 GPU 图槽下载，下载包含 fence 等待；之后部分结果又上传。这是明确存在的同步边界，但本次没有测量其实际帧时开销，不能给出性能损失比例。

**改法：**Scene 保存兼容逻辑状态，逻辑更新/查询确保依赖关系已解析；Renderer 消费只读快照。BitmapStore 明确每张可变图像的 CPU/GPU 驻留、版本和脏区域，减少反复回读。常见效果再按测量结果迁移到 GPU。

保留已验证的整数混合路径，先建立颜色/alpha 契约。不要为了统一预乘 alpha 或固定管线而破坏当前逐位匹配的格式转换与混合规则。

### 9. P2：影片播放器形成第二个主循环，音频仍有实时性风险

证据：`src/video/player.cpp:15`、`:80`；`src/bindings/movie_subops.cpp:40`；`src/audio/mixer.cpp:146`；`src/audio/device.cpp`。

`play_movie()` 阻塞执行自己的事件和呈现循环，并写死 800×600 画布，而运行器使用 1280×720。它会占用主循环，也不共享正常调度流程。影片关闭请求记录在 MovieHost，运行器主要检查 SystemState 的退出标志，退出状态有两个来源。

Mixer 在整个混音块持有同一互斥锁并分配累加缓冲，SDL 回调还可能扩容缓冲；音频在绑定调用时整段同步解码。存在主线程停顿和音频回调等待风险，尚未做延迟测量。

**改法：**MovieService 做可更新的播放状态机，逐轮提交视频帧和音频数据，由唯一运行循环处理事件。是否暂停其他脚本线程应由原版行为证据决定。画布尺寸来自会话配置。

音频先接通设备与离线推进，再引入预分配缓冲、明确所有者的控制队列和有界流式解码。音频对脚本的可观察查询应有统一采样边界，避免依赖任意回调时刻。

### 10. P2：资源、文字和配置缺少统一兼容策略

证据：`src/bindings/arc_program_provider.cpp`、`arc_resource_finder.cpp`；`src/bindings/system_subops.cpp:444`；`src/text/layout.hpp:43`；`src/text/font.cpp`；`CMakePresets.json`。

程序、图像/音频和裸文件采用不同查找入口；归档 finder 会回退扫描其他归档，损坏与不存在在部分路径被合并处理。搜索优先级、路径编码、覆盖目录和重复名字的行为应成为显式规则。

基础文本布局是逐字贪心换行，尚未实现完整禁则、注音和控制规则；测量接口忽略部分宽度、粗体、比例参数。字体依赖系统字体和逐字 fallback，跨机器测量与分页可能变化。它影响脚本行为，不只是视觉质量。

默认数据目录是共享临时目录 `obgi_data`，缺少游戏/用户隔离；公共 CMake preset 写死本地代理，默认测试目录写死单个游戏路径。构建所有模块会拉入图形、着色器和 FFmpeg 依赖，不利于单独验证 VM/格式。

**改法：**统一资源解析器并保留完整来源与错误；用 GameProfile 定义当前游戏所需的资源挂载、编码、画布和字体度量策略。把文本解析/布局和字形绘制分离，先对齐脚本可观察的尺寸、换行和分页。机器路径、代理进入本地配置；按游戏标识选择持久数据目录；允许独立构建 VM 和 formats 测试。

### 11. P2：现有测试覆盖集中在局部算法，缺少会话闭环

证据：`tests/CMakeLists.txt`、`tests/test_formats.cpp:39`、`tests/test_movie.cpp:44`、`tests/test_graphics_subops.cpp:112`；tests 中未找到序列异步 opcode 的对应测试。

优点是已有解码散列、VM 合成程序、混合向量和 Mixer 测试。薄弱处是图形/真实数据不可用时经常直接 return，报告仍显示用例通过；全部测试只有一个 CTest 入口，且没有覆盖运行器装配、异步完成、取消、存读档恢复等跨模块契约。

**改法：**分离纯单元、GPU、私有游戏数据和会话回归。缺资源要显式报告不可用；要求真实数据的流水线应在缺数据时失败。用小型合成资源覆盖常规分支，把私有游戏数据留给额外兼容套件。保留每次回归的 profile、输入、资源摘要、桩命中和后端信息。

## 建议的目标结构

| 模块 | 拥有的内容 | 边界 |
|---|---|---|
| `compat/` | opcode 描述、版本规则、证据索引、脚本 ID 映射 | 不引用 SDL/GPU |
| `vm/` | 地址空间、环形表达式栈、解释器、调度、等待与完成写回 | 只通过服务端口发起领域操作 |
| `runtime/` | EngineSession、时钟、外部事件、任务完成、生命周期 | 统一运行与取消入口 |
| `services/` | Scene、Bitmap、Message、Input、Audio、Movie、Persistence 的状态与操作 | 业务规则可脱离 VM 测试 |
| `resources/` | 挂载与查找规则、资源身份、解码缓存、内存预算 | 返回带来源和所有权的资源 |
| `backends/` | SDL、GPU、设备音频、FFmpeg、文件系统 | 实现平台设施，不拥有游戏规则 |
| `app/`、`tools/` | 参数、配置、交互运行、回放、trace/diff | 调用同一个 EngineSession |

优先使用具体服务与窄端口。时钟、IO、呈现和任务执行器等确有替换需求的边界再用接口；不需要给每个类都增加虚接口，也暂不需要 ECS、通用插件框架或完整事件溯源系统。

一次调度边界的流程应明确为：接收并编号外部事件和任务完成 → 按兼容规则更新输入/运动/等待 → 调度脚本及其领域操作 → 发布场景与音频命令 → 由后端呈现/输出。具体先后次序仍需用原版轨迹核对，不能为了架构整齐擅自移动脚本可观察副作用。

实时运行用单调时钟和实际完成事件；回放记录外部事件及异步结果被接纳的逻辑时刻，再按该记录投递。仅注入虚拟时钟而保留任意 future 就绪时机，并不能保证确定性。不能把所有异步解码强制下一帧完成并当作原版行为。

## 保存与恢复的实际边界

检查点至少包含：VM 内存和线程/调用栈/模块身份、调度与等待状态、随机数状态、场景和可变图像、文字页与渐显、输入优先级、音频播放位置/循环/淡变、视频和序列位置、游戏及资源身份。

尤其要处理脚本修改过的图槽、截图和文字层：仅保存资源文件名无法恢复它们。可以保存必要像素，或保存有界、可重建且经校验的操作描述；先以正确性决定方案，再优化容量。

保存前将已接纳的异步结果收敛到一致边界；未完成操作保存可重启描述或明确等待其完成。恢复时增加会话代数，使旧会话后台任务无法写回新状态。音频状态也需要在明确边界采样。

## 分阶段迁移与验收

| 阶段 | 工作 | 完成标准 |
|---|---|---|
| 0：可信基线 | 修复当前 RC 2 回归；描述即时/完成签名；标注桩与显式覆盖；分离测试种类 | 当前失败消失；异步分支有合成测试；报告能区分已执行与缺资源 |

不要等全部服务抽离之后才验证存档：阶段 2 应先选择一个消息等待和一个解码等待，证明其状态可恢复。每阶段保留旧路径作为对照，使用同一输入回放比较首次分歧。

推荐第一条完整验收路径是：启动 → 标题菜单 → 开始剧情 → 逐字文字 → 输入推进 → 选项 → 存档 → 重启 → 读档 → 继续，并覆盖同时播放 BGM/语音、一个场景过渡和一段影片。该路径能跨越本次发现的大多数架构断点。

## 现有设计文档需要改写的承诺

`analysis/引擎设计.md` 的分层方向仍可沿用，但以下内容应以证据和明确约束替换：

1. “固定逻辑节拍”不能与真实毫秒时钟混为一谈，`90:02` 的作用需要单独描述。
2. “所有服务可序列化”必须细化到等待、可变图像、音频和后台任务的恢复协议。
3. “全部预乘 alpha”和固定混合状态必须服从已验证的原版公式，不能成为无条件前提。
4. “异步读头拿尺寸”不一定适用于所有压缩封装，必须允许有界同步解析，并定义可观察就绪语义。
5. “替换 render 即可支持网页”低估了音频、FFmpeg、文件系统和线程设施的迁移范围，当前不应作为架构保证。
6. “脚本可观察完全一致”应有 opcode/版本/路径级验证清单；已注册数量与跑过若干帧都不能替代兼容证据。

当前最有价值的下一步，是完成阶段 0 和唯一 EngineSession 的最小版本，再通过消息等待与异步解码两个纵向切片检验新边界。
