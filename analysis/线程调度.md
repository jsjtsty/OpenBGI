# 线程调度与等待协议（任务 M，进行中）

复现：`analysis/.venv/Scripts/python.exe analysis/scripts/verify_wait_timing.py` 和 `analysis/.venv/Scripts/python.exe analysis/scripts/verify_scheduler.py`。代码依据 `out/ac2_ML.c` 中 `FUN_0049be00`、`FUN_0044d3b0`、`FUN_0044d3e0` 和各等待对象。调度器使用合成线程及回调，尚未与整机时钟对照。

【已验证】在时钟、输入查询和分配器打桩的 Unicorn 实验中，`80:5A` 的已到期/未到期分支以及 `80:5C` 的计时结束/输入触发分支与原版处理器一致。另以合成线程、脚本处理器和等待对象运行原版 `FUN_0049be00`，验证了返回码 2、3、4、5、6 的线程顺序，目标不存在时返回 3 的本轮结束行为，以及等待对象返回 0、1、-1 的调度与清理。

【静态推断】调度器基于线程标志、等待对象更新值和处理器返回码决定是继续当前线程、切换、延后还是终止。`80:5C` 的等待使用引擎时间而不是固定一帧。

【未知】完整异常恢复、原版整机调度顺序、各种异步对象的状态和返回码尚未逐一验证；本文件不能证明所有线程/输入分支。

【对 C++ 实现的直接建议】区分“处理器返回 2”和“已安装等待对象”；为 `80:5C` 保存到期时间和输入优先级，在等待结束时将 0 或 1 压入发起线程表达式栈。不要将处理器瞬时压栈数与稍后对象回调压栈数合并为一步。

【模拟】研究脚本 `vm_mt.py` 已将旧的“固定等一帧且不压结果”改为在虚拟毫秒时钟下按等待时长检查，并在计时结束时向正确线程压 0；它假设无输入、以帧推进时钟，尚不是输入中断或原版时钟实现。修改前生成的轨迹不能作为修改后的运行结果。

## 等待状态机

【静态推断】`FUN_0044d3b0` 先销毁旧对象，将新对象写线程 `+0x5c` 并置 `+0x74` bit 0；等待对象持有线程指针。`FUN_0044d3e0` 在每次处理等待线程时调用对象虚函数 +4：

| 更新结果 | 后续行为 |
|---|---|
| 0 | 保留对象和等待标志，本轮跳过该线程 |
| 1 | 析构对象、清指针和等待位，同轮可继续执行该线程 |
| -1 | 若有对象则析构并清位；本轮设置全局抑制标志，跳过后续普通线程 |
| 其他非零 | 执行可继续，但对象和等待位不会按 1/-1 路径清理；不能自行视为正常完成 |

【静态推断】若等待位被置但对象为空，`FUN_0044d3e0` 返回 -1 且不经过清理。计时对象 `CProcWaitTimingEx::FUN_00445620` 在完成时调用 `FUN_0044d2c0(param_1[1], result)`，因此压到对象保存的发起线程；时间结束压 0，输入触发压 1。对象被发送控制消息 `1` 时设置自身 `+0x28` 标志，更新函数走压 0 的完成分支。析构时如果注册过输入优先级，还会撤销注册。

| 子 opcode | 瞬时栈效果 | 调度码与等待 |
|---|---|---|
| `80:58` | 弹 1 | 保存引擎时钟当前值加参数到线程截止时间字段；返回 0 |
| `80:5A` | 压 1 | 固定返回 2；截止时间仍在未来则安装 `CProcWaitTiming` 并压 1，否则不安装并压 0 |
| `80:5C` | 弹 3，不立即压 | 安装 `CProcWaitTimingEx` 并返回 2；之后到期压 0，输入触发压 1 |
| `80:5D` | 弹 1 | 非零时设置当前线程为调度过滤目标，零时关闭过滤；返回 0 |
| `80:5E` | 弹线程 ID | 写 `DAT_0054adb0`，返回 3，请求调度器切换 |
| `80:5F` | 无 | 返回 1，转到下一线程 |
| `80:6A` | 无 | 返回 6，转到下一线程并设置本轮抑制标志 |
| `80:A0` | 弹 1、压 1 | 全局事件队列非空时写 12 字节并压 1，空时压 0；正常返回 0，不安装等待对象。两种分支经原版处理器对照（锁和释放打桩），见 `scripts/verify_system_queue.py`。 |

【静态推断】`CProcWaitTiming` 和 `CProcWaitTimingEx` 的时间基准经 `FUN_004379f0 → FUN_004a9f60 → FUN_004a9ea0` 取自 `GetTickCount` 或 `timeGetTime`，单位为毫秒并有引擎暂停/累计修正；不是帧计数。`90:02` 单独将帧率参数变换为每帧毫秒数，尚未发现它直接替换等待对象的时钟。`80:5C` 输入命中还依赖全局输入掩码与注册优先级，不能简单把任意按键当作中断。

【已验证（原版等待对象；时钟、输入查询和分配器打桩）】启用输入时，`FUN_00445620` 将输入位与 `(DAT_0052ebb0 | 0x80000181)` 相与：全局掩码为 0 时，位 `0x1`、`0x80`、`0x100`、`0x80000000` 可触发并压 1，位 `0x2`、`0x40000000` 不触发；将全局掩码设为 `0x2` 后该位也触发。另验证对象控制完成标志置位时，在未到期条件下完成并压 0。输入查询函数是桩，本实验没有验证真实鼠标/键盘映射或优先级注册。

## 调度循环

【静态推断】`FUN_0049be00` 从根链表的下一节点起依次处理：过滤目标不匹配则跳过；终止标志置位时经 `FUN_0044d740` 检查能否删除；等待标志置位先更新等待对象；本轮抑制标志置位则跳过脚本执行。否则每片段执行至处理器返回非零，或执行到 `0x100000` 条。返回码 2 保留当前线程指针并重新进入上述状态检查；3 用 `DAT_0054adb0` 查找目标线程；4 置终止位 `0x80000000`；6 设置本轮抑制并走下一线程；1、5 及其他默认值走下一线程。执行上限耗尽且末条返回 0 时同样走默认分支，不单独标记线程终止。3 指向不存在的 ID 时查找返回空，本轮循环结束，不能假设自动选择下一线程。

【已验证（原引擎调度器，合成线程和处理器）】`scripts/verify_scheduler_limit.py` 在一个线程连续执行恰好 `0x100000` 条返回 0 的模拟处理器，随后原版调度器执行下一线程；前一线程仍在链表、IP 前进 `0x100000` 且未置终止标志。该实验使用一条固定返回 0 的合成指令，不验证实际脚本中的耗时或副作用。

【静态推断】外层 `FUN_0049b8b0` 发现根线程的子链表为空后退出当前内层循环并再次执行外层重初始化，包括清理/初始化各子系统和再次创建 autoload 线程；异常处理及退出标志也会影响是否继续，因此“空链表必然无限重建”不是完整条件。

【静态推断】`CThread` 构造时 `+8 = DAT_005382a4`，随后全局计数器加一；`FUN_00432b10` 返回 `+8` 作为 ID。原始 EXE 映像中计数器初值为 0；此代码没有空闲 ID 回收逻辑，32 位回绕和其他写入路径仍需验证。`FUN_0044ccc0` 对 ID 0 特判返回空，不能将 0 当普通可切换线程；脚本依赖 ID 数值的全部场景尚未扫描。

【已验证（原构造函数）】`scripts/verify_shader_thread_ids.py` 在新映像中连续调用原构造函数，获得 ID 0、1、2。启动函数先构造空根节点再创建 autoload 子线程，因此在之前没有线程构造时 autoload 为 1；这不保证经过重启或其他初始化路径时计数器仍为初始值。
