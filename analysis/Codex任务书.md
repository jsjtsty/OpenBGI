# Codex 任务书：BGI 逆向研究（只研究，不写正式代码）

## 0. 背景与分工

目标：为 Amairo Chocolate 2（BURIKO General Interpreter / Ethornell 1.667.3，`ac2_ML.exe`，32 位 x86）做一个跨平台兼容引擎 OpenBGI（SDL3 等）。

分工：

- **Codex（你）**：只做研究。分析反编译源码、探索算法、解密和验证格式、写实验脚本、产出格式规范和语义表。
- **Claude**：之后根据你的研究成果，编写 OpenBGI 的正式代码。

所以你的产出是**知识和证据**，不是引擎。

## 1. 硬性规则

1. **不要创建或修改 `D:\Projects\C++\OpenBGI\src\`**，也不要建 CMake 工程、不要写引擎代码、不要设计引擎架构。
2. 实验代码只放在 `analysis\scripts\`（JS 或 Python 均可），临时数据放 `analysis\out\`。实验脚本要能一键复现，头部注释写明用法和依据的函数地址。
3. 每条结论必须标注可信度：
   - **已验证**：有可复现的实验或数据佐证（例如长度、校验、可读内容、与已知格式一致）。
   - **静态推断**：只来自阅读反编译代码，未经实验。
   - **未知**：明确写出尚不清楚什么、需要什么才能弄清。
4. 不要把推断写成事实。发现与之前文档矛盾的地方，直接修正并在文末「修订记录」里说明。
5. 不要两个任务同时访问同一个 Ghidra 项目（会有锁冲突）。需要时优先读 `analysis\out\ac2_ML.c`、`ac2_ML.functions.tsv`、`ac2_ML.symbols.txt`、`ac2_ML.strings.txt`。
6. 不要把游戏资源复制进仓库目录之外的任何地方，也不要提交解包出的素材。解包结果只放在 `analysis\out\` 下，且不参与正式产出。
7. 已知笔误：`VM分析.md` 里的 `DCFS FORMAT 1.00` 应为 `DSC FORMAT 1.00`，请修掉。

## 2. 已有基础（先读）

- `analysis\VM分析.md`：VM 主循环、线程、栈、主 opcode 表、两级分发（11 张子 opcode 表共 796 项）。
- `analysis\子opcode表.tsv`：主 opcode、子 opcode、处理器地址。
- `analysis\scripts\extract_dsc.js`：DSC 解码器原型，已能解出 `ipl._bp`、`framework._bs`，但未与原引擎逐字节对照。
- `analysis\out\`：Ghidra 导出的反编译 C、函数索引、符号、字符串、导入表。
- 游戏目录：`E:\Games\Amairo Chocolate 2\`（只读，不要改动）。

已确认的资源事实：

- `*.arc` 为 `BURIKO ARC20`：16 字节头（12 字节魔数加 4 字节条目数），每条目 0x80 字节，前 0x60 字节为名称，其后是相对数据区的偏移和大小，数据区起点是 `16 + 条目数 * 0x80`。
- 脚本、配置、`sysgrp` 等用 `DSC FORMAT 1.00`；CG、立绘、背景、wipe 遮罩用 `CompressedBG___`；语音和 BGM 为 0x40 字节的 `bw  ` 头加标准 Ogg Vorbis；视频有 `.mpg` 和自有的 `BF_Movie` 格式（`.bm`）。

## 3. 任务

按顺序做。每个任务结束时更新对应文档，并给出复现步骤。

### 任务 A：DSC 解码器的验证与加固

目标：确认 DSC 解码器对全部数据都正确。

做什么：

1. 用 `extract_dsc.js` 的算法（可重写成 Python，作为交叉验证）解开游戏里**所有** DSC 成员：`autoload`、`system`、`sysprg`、`sysgrp`、`data01100`、`data01120`、`data01121`、`data01130`、`data01131`、`data06000` 等。
2. 检查：解压长度与头部一致；没有越界和非法回溯；解出的数据结构合理（例如脚本以 `BurikoCompiledScriptVer1.00` 开头）。
3. 在 `ac2_ML.c` 里复核解码函数（`FUN_00470f00`、`FUN_00471170` 及其调用者），确认 Huffman 建树规则（同码长按符号序排序、左右分配）、位序和回溯距离的解释没有遗漏分支。
4. 记录所有成员的解压前后大小，产出清单 `out\dsc_manifest.tsv`（arc、成员名、存储大小、解出大小、前 16 字节、是否通过）。

产出：`analysis\DSC格式.md`（头部布局、密钥流、建树、位流、LZ 规则，附可信度）和修订后的实验脚本。

### 任务 B：CompressedBG 图像格式

目标：完整弄清 `CompressedBG___` 的解码，并能导出为 PNG 供肉眼检查。

做什么：

1. 在 `ac2_ML.c` 里找到处理 `CompressedBG___` 的解码函数，逆出头部字段（宽、高、位深、各种长度、校验种子等）、熵解码和像素重建（可能含 Huffman、行预测或 DCT 类步骤，以代码为准，不要凭记忆）。
2. 用 Python 写实验解码器，至少覆盖 `data02200.arc`、`data02210.arc`、`data02260.arc`、`data02290.arc`（wipe 遮罩）、`data02291.arc` 里的若干张图，导出 PNG 到 `analysis\out\cbg_samples\`。
3. 检查是否有带 alpha 的变体、不同位深和遮罩图的特殊处理；同时调查 `BSE` 头在这里或别处是否出现。
4. 记录解码速度瓶颈（图很大，后续会影响引擎设计）。

产出：`analysis\CBG格式.md`，附样例 PNG 清单。如果有成员解不出来，列出名称和现象。

### 任务 C：脚本容器格式与反汇编器原型

目标：弄清游戏脚本文件结构，并写一个**研究用**的反汇编器验证主 opcode 的操作数宽度。

做什么：

1. 解析 `BurikoCompiledScriptVer1.00`：文件头、代码段、符号表、导入表（外部模块与符号）、字符串或数据区，写清各字段的偏移和含义。弄清 `ipl._bp`、`_bp`、`_bs`、`_bsi` 之间的关系和各自的作用。
2. 在 `ac2_ML.c` 中找到装载脚本的函数（`FUN_0044ce40` 附近及其调用者），确认装载后如何把符号表、导入表映射成运行时地址和调用目标。
3. 写 `scripts\bgi_dis.py`（研究用），按 `VM分析.md` 的主 opcode 表反汇编全部脚本。
4. 验收：对游戏里全部脚本（`data01120`、`data01121`、`data01130`、`data01131`、`sysprg`、`system`、`autoload`）做线性扫描，**不出现未知 opcode**，每个函数都能刚好走到结尾（不跨过相邻函数的起点）。有失败就说明原因，并回头修正操作数宽度表。
5. 输出所有子 opcode 的**使用频次统计**到 `out\subop_usage.tsv`（主 opcode、子 opcode、出现次数、出现于哪些脚本）。后面的任务 D 靠这个排序。

产出：`analysis\脚本格式.md`、`scripts\bgi_dis.py`、若干反汇编样例文本（不必全量提交）。

### 任务 D：子 opcode 语义表

目标：弄清游戏实际使用的子 opcode 在做什么。

做什么：

1. 按任务 C 的频次统计**从高到低**分析，不要从地址顺序平铺。先做覆盖了 95% 调用次数的那部分。
2. 对每个子 opcode 记录：
   - 弹出几个参数、各自含义（位置、颜色、对象 ID、资源名指针、时间、标志位等）
   - 有无返回值或压栈结果
   - 额外的立即数操作数及其字节宽度
   - 对应的引擎子系统和调用链（用 RTTI 类名，如 `CDspObjSprite`、`CFontManager`、`CBurikoWaveBox*`、`DCMovieRenderer` 等）
   - 副作用（是否改变全局状态、是否会让线程等待、返回给调度器的代码）
3. 利用 `framework_symbols.tsv` 里的符号名（`WaitBS`、`_DrawBG` 等）和脚本里的调用上下文佐证命名。
4. 同时分析主 opcode 里标注为「待分析」的 `0x50–0x5F`、`0x77–0x7E` 等项。
5. 写清线程等待对象的协议（`FUN_0044d3b0`、`FUN_0044d3e0`）：什么情况下脚本线程会被挂起、靠什么条件恢复。

产出：`analysis\子opcode语义表.md`，每条标注可信度。未分析的条目保留在表里并标明「未分析」，不要省略。

### 任务 E：其他数据格式

每项产出一份格式说明，并附实验解析脚本：

1. `BGI.gdb`（`BURIKO GDB 3.00`）和 `BGI.hvl`：内容和用途。
2. `.sud` 存档：头、变量区、截图缩略图、与脚本全局变量的对应关系。`UserData` 和 `原版备份` 里有样本可对照。
3. `sysgrp.arc` 里的 `SGCnf*`、`_bsi` 等配置类文件。
4. `BF_Movie` 的 `.bm`（如 `ef_love.bm`、`ef_shuchu.bm`）：头部、帧数据，以及它是否真的是视频、还是特效描述。
5. `data02280.arc` 里的 `.mpg`：确认是标准 MPEG-PS 还是带特殊处理。

### 任务 F：渲染和特效行为（只做调研）

目标：弄清原版 D3D9 渲染的行为，给后面用 SDL3 重写做依据。

做什么：

1. 梳理 `d3d9` 的使用方式：设备创建参数、分辨率、缩放策略、纹理格式、混合状态、采样器设置。
2. 找出 `SHADER` 相关资源，确认着色器是内置字节码还是从文件读取；能提取就提取，并说明用途。
3. 梳理 wipe/过渡（`ac2_wipe_*_mask`）、`ef_*.bm` 特效在引擎里的使用方式和参数。
4. 梳理文字渲染：字体来源、`CFontDx`/`CFontManager` 的排版逻辑、描边和阴影、行距、ruby、换行规则（禁则）。

产出：`analysis\渲染与文字.md`。
