### 任务 L：主 opcode 未知项

对象（`VM分析.md` 表中「待分析」或未实现）：`0x0B`、`0x10`、`0x11`、`0x42`–`0x49`、`0x50`–`0x5F`（`0x5C` 不在表里，确认）、`0x64`–`0x66`、`0x6C`–`0x6E`、`0x73`–`0x75`、`0x77`–`0x7E`。另有 `FUN_0049d7c0` 运行时替换 8 个主 opcode（`09 0A 0C 60 61 62 6A 6F`）的事。

做什么：

1. 每个主 opcode：操作数编码、弹/压、语义、是否可能返回非 0 调度码。数学类（`0x42`–`0x49`）要给出精确公式，**浮点要写清用的是 x87 还是 SSE、是否有舍入模式依赖**，最好用 Unicorn 直接调用并附若干组输入输出向量（`tests` 里会作为对照数据）。
2. `FUN_0049d7c0`：什么时候被调用、参数从哪里来、替换前后行为差异（替代实现多出来的「额外内存处理」是什么）。这决定新引擎要不要实现「写监视」（`0x74`、`0x75` 与此相关吗？）。
3. `0x0B`、`0x10`、`0x11` 的确切语义（`0x11` 到底是设置 SP 还是调整 SP，边界检查条件，`0x10` 压的是原始 SP 还是带标签地址）。
4. 脚本里这些 opcode 的实际使用：`out\bp_linear_all.tsv` 与 `out\bs_*` 里是否真的出现。**没出现过的只需要写操作数编码和一句话语义，不用逐个验证。**
5. `FUN_0049d1f0`、`FUN_0049d0a0`（地址解析）：所有地址标签（高 6 位）的含义和边界检查规则。我们现在只实现了 0=全局内存、1=程序、2=数据栈、3=堆（新增，非原版），原版是否还有其他标签？全局内存的真实范围和 `80:70`（分配虚拟地址空间）的关系是什么？

产出：新文档 `主opcode语义.md`（不要改 `VM分析.md` 的表，只在表里给新文档加链接）。

### 任务 M：线程等待协议与调度细节

目前 C++ 里 `80:5C` 只做「等 1 帧」，这与 `子opcode语义表.md` 里的描述（弹输入优先级、启用输入中断标志、等待时间，安装 `CProcWaitTimingEx`，计时结束压 0）**不一致**，是 VM 里最明确的已知偏差。

做什么：

1. `FUN_0044d3b0`、`FUN_0044d3e0` 及相关等待对象类：挂起条件、恢复条件、恢复时往栈里压什么值（压在谁的栈上、压几个）、`80:5A`/`80:5C`/`80:5F`/`80:6A`/`80:A0` 等等待类子 opcode 各自安装什么等待对象。
2. 等待对象的 `ready` 判定用什么时钟（毫秒时钟还是帧计数？`90:02` 设定的帧率与等待的关系），是否受「输入中断」打断，打断时返回什么。
3. `FUN_0049be00` 里与调度有关但 Python 原型没有复现的部分：线程列表为空时重新初始化并重建 autoload 线程的完整条件；`DAT_0054adb0`（SwitchThread 目标）的来源；返回码 3、5、6 的完整语义；每片段 0x100000 条指令用尽后线程的状态。
4. 回答：线程 ID 由什么分配（连续整数？可复用？），脚本里是否依赖 ID 数值（例如与 0 比较）。
5. 输出用 Unicorn 或静态证据佐证的一个**状态机描述**，让 Claude 能直接改 `src/vm/scheduler.cpp` 和 `core_subops.cpp`。

产出：`线程调度.md`。
